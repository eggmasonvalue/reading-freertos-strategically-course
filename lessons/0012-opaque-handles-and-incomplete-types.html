A handle you can't open

C has no private keyword, yet the kernel hides an entire data structure from every caller and the compiler itself enforces it. This lesson is the mechanism behind that — precisely why it works, exactly what it costs, and when the cost is not worth paying.

Why this lesson: C11 argued a type is a wall for the generator and the machine-checked contract. The opaque handle is that argument made concrete in a language with no access control: it turns "you may not touch my internals" from a code-review plea into a compile error. But it is a tradeoff, not a free good — and a strategic reviewer must be able to price both sides.

Specimen: the queue you're structurally forbidden to see

Two files. First, the entire public face of a queue — ./reference/FreeRTOS-Kernel/include/queue.h:

/* queue.h — the PUBLIC face, all a caller ever gets */
struct QueueDefinition;   /* forward declaration only — no body */
typedef struct QueueDefinition * QueueHandle_t;

./reference/FreeRTOS-Kernel/include/queue.h — lines 50–51

The caller sees the name of a struct and a pointer to it — nothing else. The body lives in a different translation unit entirely — ./reference/FreeRTOS-Kernel/queue.c:

/* queue.c — the PRIVATE body, invisible to every caller */
typedef struct QueueDefinition {  /* comment: old name kept so debuggers still work */
    int8_t * pcHead, * pcWriteTo;                 /* storage cursors      */
    union { QueuePointers_t xQueue;
            SemaphoreData_t xSemaphore; } u;      /* queue OR semaphore   */
    List_t xTasksWaitingToSend, xTasksWaitingToReceive;
    volatile UBaseType_t uxMessagesWaiting;
    UBaseType_t uxLength, uxItemSize;
    volatile int8_t cRxLock, cTxLock;             /* + config-gated fields */
} xQUEUE;

The mechanism — precisely why the wall holds

Because the header only forward-declares struct QueueDefinition, at every call site that struct is an incomplete type: a type whose name is known but whose size and members are not. The C standard is exact about what you may and may not do with one, and that asymmetry is the whole trick:

allowed on an incomplete type

Form and pass a pointer to it (all object pointers have known size/representation), store it, compare it, return it. Everything the caller legitimately needs.

forbidden by the compiler

handle->uxLength (needs member layout), *handle to copy it, sizeof(*handle) (needs size). The moment a caller reaches inside, translation fails.

Read this carefully — it's the crux The hiding is not convention, documentation, or discipline. It is a property of the type system: to access a member the compiler must know the layout, and you have deliberately withheld the layout from that translation unit. So the guarantee "callers cannot depend on my internals" is enforced by cc, on every build, with no reviewer in the loop. That is C11's "machine-checked wall," realized in the one mechanism C gives you for it.
Deep dive — why a pointer to incomplete type is fine but a value isn't

A pointer is a fixed-size, fixed-representation object regardless of what it points at — the compiler can allocate, copy, and pass it knowing only "it's a pointer." Member access (->), dereference-to-copy (*p), and sizeof(*p) all require the pointee's layout, which an incomplete type doesn't provide. This is exactly the seam the pattern exploits: expose the thing whose handling needs no layout (the pointer), withhold the thing whose handling would (the body). It's also why the constructor must live on the inside — only queue.c knows sizeof(Queue_t), so only it (or the allocator it calls) can create one. The caller literally cannot, and that inability is the feature.

Read the payoff through C11's four blades

  • Wall for the generator. An LLM cannot emit q->uxMessagesWaiting++ to "optimize" — it will not compile. The only path through is the published functions (uxQueueMessagesWaiting()). The type forecloses a whole genre of plausible slop before review.
  • Machine-checked, forever. Every hidden field — the two waiting-lists, the lock counters, the union that makes a queue and a semaphore the same struct (lesson A2) — can change freely in queue.c and no caller can break, because none could depend on it. The seam is compiler-guarded, not hope-guarded.
  • Durable / ABI-stable. Add a field, reorder the struct, swap the union layout — the interface the caller compiled against (a pointer) is unchanged. (See the ABI deep-dive.)
  • Density. The caller reasons about one word — "a queue" — instead of eleven fields. Eleven fields of cognitive load, hidden behind a single token.
Deep dive — the second-order win: ABI stability and separate compilation

Because callers only ever see a pointer, the kernel's binary layout of struct QueueDefinition is not part of its application binary interface. Concretely: FreeRTOS can ship a precompiled kernel, add a field to the queue struct in a point release, and your application object files — compiled against the old header — still link and run, because nothing in them encoded the struct's size or field offsets. Turn the struct transparent and that property evaporates: the field offsets are now baked into every caller's object code, so any change forces a full recompile of the world and silently corrupts any binary that wasn't rebuilt. Opaqueness is what makes independent recompilation and binary distribution safe. For a kernel used across thousands of projects and toolchains, that is not a nicety — it's load-bearing.

A revealing detail: the struct's comment — "old naming convention kept so as not to break kernel-aware debuggers" — shows the hiding is deliberately one-way. Opaque to normal C callers; still named so a debugger can crack it open. Hiding is aimed at callers who might create dependencies, not at maintainers who need to see in. That precision is itself a documented decision (lesson A3).

The honest price (there is always one)

Opacity is not free, and pretending it is would fail C11's own "state the tradeoff" test. What it costs:

  • Allocation moves inside. The caller can't know sizeof, so it cannot stack-allocate a queue. Someone else must allocate. This is exactly why the kernel ships xQueueCreate (heap) and xQueueCreateStatic (you hand it a buffer): the second API exists because the type is opaque. The pattern created an API obligation.
  • Indirection and no inlining. Every access goes through a function call across a translation-unit boundary; the compiler can't inline field reads it can't see. A measurable, if usually small, cost.
  • More ceremony. You must write and maintain accessor functions for anything callers legitimately need (uxQueueMessagesWaiting() exists so callers can read a count they can't reach directly).
The strongest case against opaque handles
  1. Premature hiding is real complexity. For a two-caller internal helper, an opaque type + constructor + accessors is more code and indirection than just exposing a plain struct. You can pay information-hiding tax where there's no information worth hiding.
  2. It fights the debugger and the optimizer. Opaque types make some tooling and inlining harder; a transparent struct behind a "don't touch these fields" convention gets you 80% of the discipline with none of the indirection.
  3. The compiler's help is coarse. Opacity stops member access, but it doesn't make illegal states unrepresentable (lesson C13) — you can still pass the wrong handle. It's one specific wall, not a fortress.

Synthesis. Every point is true, and each one sharpens when to reach for the pattern rather than refuting it. Opacity earns its cost precisely at a published, widely-used, ABI-stable boundary with many callers you don't control — which is exactly the kernel's situation, and exactly why FreeRTOS pays the tax here. For an internal helper with two callers in the same file, the steelman is correct: a plain struct is the deeper choice, and hiding would be ceremony. So the rule isn't "always hide"; it's "hide in proportion to the number of callers and the stability you must promise them." That proportionality is the judgment — reflexively opaque everywhere is as junior as reflexively transparent everywhere.

Red flag to name in reviews A struct definition sitting in a public header whose fields callers have no business touching — especially one an LLM emitted "so the caller can read X directly." Say it: "This type is transparent — its layout is now every caller's dependency and part of our ABI. If this is a published boundary, forward-declare it, move the body to the .c, and expose the accessor we actually need." And its inverse, so you're not dogmatic: "This is a 2-caller internal helper — the opaque wrapper is ceremony here; a plain struct is clearer."
