Comments that add information, not noise

Most comments are worthless because they repeat the code. The valuable ones capture what the code cannot say — the abstraction, the contract, the reason. Ousterhout goes further: writing them first is a design tool that exposes shallow modules before you build them. But a large, serious camp says comments are a smell — so we'll take that seriously and find the exact line.

Why this lesson: In the AI era comments do double duty — they're the spec a reviewer reads and the intent an LLM is meant to honor. But models emit exactly the wrong kind (restating the line above). Knowing which comments carry information — and using them to drive design — is the skill. This pairs directly with A3 (the comment that records a decision).

The distinction that matters: interface vs implementation

  • Interface comment — everything a caller must know to use the thing that isn't in the signature: what it does, contracts, units, side effects. It lets you use the module without reading its body.
  • Implementation comment — how/why the body works, for a maintainer: the non-obvious algorithm, the tricky invariant.

Cardinal rule: an interface comment must not describe implementation details, or you've leaked internals into the interface (information leakage in prose). The caller's document is about what; the maintainer's about how.1

Specimen: the header comment on xTaskCreate

/**
 * Create a new task and add it to the list of tasks that are ready to run.
 *
 * Internally, within the FreeRTOS implementation, tasks use two blocks of
 * memory. ... If a task is created using xTaskCreate() then both blocks of
 * memory are automatically dynamically allocated ...
 */

./reference/FreeRTOS-Kernel/include/task.h — comment block, lines 301–394

Why this comment earns its keep It states the abstraction ("create a task, make it ready to run") in one line — which the signature alone doesn't say — then tells the caller a fact they genuinely need but cannot see in the type: this variant dynamically allocates two blocks of memory. That one sentence is why a caller can choose between xTaskCreate (heap) and xTaskCreateStatic (their buffer) without reading either body — the exact allocation tradeoff from C12. The comment does what the type couldn't: it carries the part of the contract C can't express.

The power move: write the comment first

Ousterhout's most useful habit: write the interface comment before the code.1 Two payoffs, and the first is the deep one:

  • It's a design check that fails cheap. If you can't describe the module simply — the comment runs long, sprouts caveats, or keeps naming internals — the module is shallow or leaky, and you've learned that at the moment of least sunk cost, before writing a line of body. That's A2's depth test, run at design time. The comment is a cheap prototype of the interface.
  • It sets the abstraction. You design to the description, not the description to the code, so the interface stays about what, not how.

The AI translation: the interface comment is the prompt-and-contract. Write it first, hand it to the model, and it's both the instruction and the acceptance test — if the generated body doesn't satisfy the comment you wrote, you have an objective failure, not a vibe. A model that writes the comment after merely describes whatever it produced; you want the comment to constrain the code, not narrate it.

The strongest case against comments ("self-documenting code")
  1. A comment is an apology for unclear code. The Clean-Code position: if you need a comment to explain what code does, rename and extract until the code says it itself. Every comment you delete by improving names is a maintenance liability removed.
  2. Comments rot and lie. Nothing forces a comment to agree with the code (same defect as names, D17). An out-of-date comment is worse than none — it actively misleads. Unchecked prose is a liability by construction.
  3. They duplicate and distract. Most comments restate the adjacent line; they add reading volume and visual noise while carrying no information.

Synthesis. The steelman is right about the comments it's describing — and every one of those is an implementation-mechanics comment (the "what/how" of a line of code). For that category, self-documenting code wins outright: rename, extract, delete the comment. But the argument has a hole it can't cover, and it's exactly the category Ousterhout cares about: some information is not derivable from the code at all, however clean. Three kinds, specifically — (a) the rationale: why this way and not the obvious alternative (A3's rejected options aren't in the code by definition — the code is what you chose, not what you rejected); (b) the abstraction as a contract: an interface comment lets a caller skip reading the body — no amount of clean code does that, because reading clean code is still reading the body; (c) units, ranges, and non-local invariants the type can't hold (C14's contracts in prose). And the "rot" objection, taken seriously, doesn't kill comments — it tells you which ones to write: comment the things that don't change when the mechanics change (rationale, contract, abstraction) and never the mechanics themselves, which the code already shows and which rot fastest. So the defensible position is precise: delete every comment that restates the code; write the ones that carry what the code structurally cannot — and prefer stable interface comments over volatile implementation ones. Self-documenting code and Ousterhout aren't in conflict once you sort comments by whether their information is derivable from the code.

Deep dive — the one-question test for whether a comment should exist

Ask: is this comment's information derivable from the code by a competent reader? If yes — i++; // increment i, or a comment restating a well-named function — delete it and, if needed, improve the name. If no — why we chose this over the obvious alternative, the unit is milliseconds, this must be called with the scheduler suspended, the buffer is caller-owned — it's carrying information that does not exist anywhere in the code, and it must be written down or it's lost. This single test dissolves most comment arguments: the two camps are usually talking about different sides of it. It also explains why interface comments are the highest-value kind: "what this does and how to use it without reading it" is never derivable from the body at a glance — that's the entire point of an interface.

Red flag to name in reviews A comment that restates the code (i++; // increment i) — pure noise, the LLM's favorite — or an interface comment describing internals a caller shouldn't depend on. Say it: "This comment repeats what the code already says — delete it and let the name carry it. If there's a why, a contract, or an abstraction to state, write that instead."
