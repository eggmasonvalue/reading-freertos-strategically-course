One list to rule them all

Faced with "the scheduler needs a list of ready tasks," the tactical instinct is to build a ReadyTaskList. The kernel built something stranger and far more powerful: a list that has never heard of a task. That choice is why five functions run the whole scheduler.

Why this lesson: An LLM, handed one caller, writes code specialised to that one caller — a ReadyTaskList with addTask/removeTask. It looks tidy and it is a trap: shallow, un-reusable, and it drags the caller's meaning into the module. The counter-skill is judging when a slightly more general interface would be simpler and deeper. Today the kernel shows you the payoff at full scale.

The idea: "somewhat general-purpose" is usually deeper

Ousterhout's Ch. 6 rule: make a module's interface somewhat general-purpose — general enough to serve several needs, not so general it serves none.1 The counter-intuitive part is that this usually makes the module simpler, not more complex: a general interface has fewer methods (they each do more), and it forces the specialised, changeable knowledge out of the module and up to the caller — which is exactly the information-hiding you practised in Lesson 4, run in reverse.

general deeper

The module knows a mechanism (order things by a number). It does not know what the number means. One implementation, reused everywhere the mechanism fits. The meaning lives at the call site, where it belongs.

special shallower

The module is built for today's one caller — names, types and rules all encode that caller's semantics. It can't be reused, and it has absorbed knowledge (what "ready" means) that now can't change without touching it.

Specimen: the list that doesn't know what it holds

Open ./reference/FreeRTOS-Kernel/list.c. The entire public engine is five functions:

/* list.c — the whole API. Nothing here mentions "task". */
void        vListInitialise( List_t * pxList );
void        vListInitialiseItem( ListItem_t * pxItem );
void        vListInsertEnd( List_t * pxList, ListItem_t * pxNew );  /* O(1) at index    */
void        vListInsert( List_t * pxList, ListItem_t * pxNew );     /* sorted by value  */
UBaseType_t uxListRemove( ListItem_t * pxItemToRemove );

./reference/FreeRTOS-Kernel/list.c — lines 49, 89, 105, 139, 217

What makes it general is two fields on the list item, and a discipline of not looking too hard at either:

/* list.h — the two hinges of generality */
struct xLIST_ITEM {
    TickType_t xItemValue;   /* the sort key. "In most cases used to sort in
                                ascending order." The list never asks what it MEANS. */
    ...
    void * pvOwner;            /* back-pointer to whatever owns this item.
                                A void*. The list never dereferences it. */
};

./reference/FreeRTOS-Kernel/include/list.h — lines 144–152

That's the whole trick. The list orders items by a TickType_t number and carries a void * back to the owner. It has no idea whether the number is a time, a priority, or a lottery ticket — and no idea that the owner is a task. Now watch tasks.c feed that same field two completely different meanings:

/* tasks.c — a delayed task: the sort key is a WAKE-UP TIME */
listSET_LIST_ITEM_VALUE( &( pxCurrentTCB->xStateListItem ), xTimeToWake );   // lines 8682–8683

/* tasks.c — a task waiting on an event: the sort key is (inverted) PRIORITY */
listSET_LIST_ITEM_VALUE( &( pxTCB->xEventListItem ),
                         configMAX_PRIORITIES - uxNewPriority );                // lines 2923–2927

./reference/FreeRTOS-Kernel/tasks.c — lines 8682–8683 (wake-time) and 2923–2927 (priority)

Same field, same insert function, opposite semantics — and the list module is untouched, because it was never told the meaning in the first place. On that one general engine the kernel builds, at last count: the ready lists (one per priority), two delayed lists (current + overflow), the pending-ready, suspended, and waiting-termination lists — plus, from Lesson 4, every queue's tasks-waiting-to-send/receive. One implementation; a dozen jobs.

Verdict Generality made this module smaller (five functions) and deeper (it powers the entire scheduler) and reusable (a dozen call sites). The specialised, volatile knowledge — "this number is a wake time," "the owner is a TCB" — was pushed up to the callers via xItemValue and a void * pvOwner. That is Ch. 6 and Ch. 5 working as one move: generalise the mechanism, hide the meaning.

What this does not claim. The rule is "somewhat general-purpose" — the adjective is load-bearing. It does not say make everything generic, configurable, or pluggable. The list commits hard to "ordered by a TickType_t, doubly-linked, intrusive"; it is general over meaning and specific about mechanism. Push past that line — a comparator-pluggable, allocator-parameterised container framework — and you buy flexibility no caller uses and a module no one can read. The claim is that the sweet spot usually sits slightly more general than today's one caller, not at maximum generality.

Deep dive — the price of the void *: generality trades type-safety for reuse

The hinge that makes the list general — void * pvOwner — is also a deliberate hole in the type system, and seeing the tradeoff is the point. Because the owner is a void *, the list can carry a TCB, a queue, a timer — anything — which is exactly the reuse we're praising. But the compiler now cannot check that what you put in is what you take out: listGET_LIST_ITEM_OWNER hands back a void * the caller must cast to the right type by hand, and a wrong cast compiles cleanly and corrupts at runtime. So generality here is bought with a connascence of type (lesson A6) that the compiler no longer polices — the caller and the list silently agree on the real owner type. FreeRTOS judges the trade worth it because the alternative (a dozen type-safe special-purpose lists) is worse on every other axis. That's the honest shape of the decision: the void * is not sloppiness, it's the currency generality is paid in — and lesson C13 is about knowing exactly where C makes you pay it.

The strongest case against generalising (steelman)

"Build the general thing" has a powerful, correct-sounding opposition. State it at full strength, then synthesise.

The case against
  1. YAGNI. You have one caller. Build for it. Generalising for imagined future callers is speculative generality — the textbook waste — and the abstraction you guess now is usually the wrong one.
  2. General is less obvious. A ReadyList.addTask() reads itself; vListInsert(&list, &item) where the item's xItemValue secretly means priority is a puzzle. The specialised name carries intent the generic one hides.
  3. Generality costs safety and speed. The void * owner and untyped sort key throw away compiler checks and can add indirection — a special-purpose structure keeps its types and can be tuned.

The synthesis. The steelman is right about speculative generality and the scoped claim already forbids it. The tell is in Ousterhout's own framing: generalise when it makes the module simpler right now, not when it adds machinery for a hypothetical. The list qualifies because "order things by a number" is genuinely simpler than "track ready tasks by priority" — fewer concepts, not more — so it's not a bet on the future, it's a cleaner present (this is the exact opposite of lesson B9's over-engineering trap, and you must be able to tell them apart). Point (2) is a real cost the kernel pays back with convention — the xStateListItem/xEventListItem names at the call site restore the intent the generic core dropped. Point (3) is true and honest (see the fold above): generality is paid in type-safety. So the position is not "always generalise" — it's "prefer the slightly more general interface when it is also simpler; refuse it when it's only a guess about tomorrow."

Munger inversion — generality dies at both ends Invert "somewhat general-purpose" and you get its two ways to die. Too special: you bake one caller's meaning into the module, and the day a second caller appears you can't reuse it — specialisation is a one-way door. Too general: you build the configurable framework for callers who never arrive, and every reader pays for flexibility no one uses — that's just B9's leakage with better manners. The list lives exactly between: general over what varies (the meaning of the number), specific about what doesn't (it's a sorted doubly-linked list). Ask of any interface: which of these two deaths is it closer to?

What over-specialisation would have cost

Take the LLM-tidy path: a ReadyList keyed by priority, a separate DelayedList keyed by time, a SuspendedList, and so on. Each "works." Collectively they are the disaster Module A keeps circling:

  • Five functions become thirty — every list re-implements insert/remove with its own names. Interface size explodes; every one is shallow.
  • The doubly-linked-list decision leaks into a dozen modules (information leakage) — fix a pointer bug once, fix it twelve times.
  • The meaning gets baked in: a ReadyList that knows it sorts by priority can't be reused the day you need to sort by wake time. Specialisation is a one-way door.

But note the discipline word: somewhat. The list isn't infinitely general — it commits to "ordered by a TickType_t, doubly-linked, intrusive." That commitment is what keeps it five functions instead of a configurable container framework. General enough to be reused; specific enough to stay tiny. Finding that line is the judgment.

Red flag to name in reviews An interface whose names and types encode the semantics of its single current caller — addReadyTask, a struct member called priority in a container that only ever sorts. The words: "This is specialised to today's one caller. What's the underlying mechanism? Name the interface after that, push the meaning to the call site, and it'll get simpler and reusable at once."
