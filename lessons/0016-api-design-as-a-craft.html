The details that make an API humane

Types set the walls; craft decides whether living inside them is pleasant or a trap. This closes Module C with the small, repeatable API judgments — dual interfaces, argument order, the boolean trap — that separate an interface people use correctly by default from one they fight. And it prices the tension between "hard to misuse" and "small."

Why this lesson: Bloch's thesis1 — "APIs should be easy to use right and hard to use wrong." That property is exactly what stops LLM-generated call sites from being subtly wrong: when the correct call is the obvious one, the model (and the junior, and you-at-2am) falls into the pit of success. But craft maxims collide with each other, and knowing which one wins when is the real skill this lesson trains.

Specimen 1 — the dual interface (context baked into the type)

The kernel never lets you call a blocking queue function from an interrupt. It ships a separate, ISR-safe twin of each:

/* task context — may block, takes a timeout */
BaseType_t xQueueSend( QueueHandle_t xQueue, const void * pvItemToQueue,
                       TickType_t xTicksToWait );

/* interrupt context — never blocks; reports if it woke a task */
BaseType_t xQueueSendFromISR( QueueHandle_t xQueue, const void * pvItemToQueue,
                              BaseType_t * pxHigherPriorityTaskWoken );

./reference/FreeRTOS-Kernel/include/queue.h — xQueueSend · xQueueSendFromISR (macro, line 1286, verified)

Why two functions beats one flag They could have written one function with an isFromISR boolean. Instead the calling context is baked into the function's identity. Three payoffs: (1) the wrong call is hard to write — you can't pass a timeout from an ISR because the parameter isn't there; (2) the FromISR suffix makes an audit trivial — grep it and every ISR-reachable path is named; (3) it's self-documenting at the call site. Context that matters became part of the name and signature rather than a runtime argument — the craft face of C11's "the signature is the spec."
Deep dive — why blocking in an ISR is catastrophic (the reason the split exists)

"Blocking" in FreeRTOS means: remove the current task from the ready list and switch to another until some event. But an interrupt doesn't run in a task — it preempted whatever was running and has no TCB of its own to suspend. Ask an ISR to "block" and there is nothing coherent to block; the scheduler's invariants break, and depending on the port you get a corrupted stack, a missed context switch, or a hard fault. This isn't a style preference — a blocking call from an ISR is undefined behavior at the scheduler level. So the dual interface is enforcing a genuine, catastrophic, and silent constraint: the danger is invisible in casual reading and its symptom is far from its cause. That severity is precisely what justifies doubling the function count (see the steelman) — the split converts a catastrophic-but-silent runtime bug into a can't-write-it-wrong compile-time shape. The pxHigherPriorityTaskWoken out-param is the other half: the ISR can't yield mid-flight, so it records whether a yield is owed and the caller performs it on exit via portYIELD_FROM_ISR() — a deferred context switch, because even yielding must wait for a safe point.

Specimen 2 — the boolean trap, dodged

Note what xQueueSendFromISR's third parameter is not: a bare bool. It's BaseType_t * pxHigherPriorityTaskWoken — a named out-parameter. A lesser design returns a bare bool and leaves the caller to guess what true meant; here the named pointer says at the call site exactly what's being reported:

xHigherPriorityTaskWoken = pdFALSE;
xQueueSendFromISR( q, &data, &xHigherPriorityTaskWoken );
/* ... the name carries the meaning; no mystery boolean */
portYIELD_FROM_ISR( xHigherPriorityTaskWoken );
The boolean trap (Bloch's classic) A bare boolean parameter — doThing(true) — is opaque at the call site: the reader can't tell what true selects without opening the docs. Worse, two booleans and you're one swap away from a silent bug the compiler can't catch (both are bool — C13's "same type" hole, in miniature). Fixes: a named enum, two well-named functions (as FromISR does), or a named out-parameter. When you see foo(x, true, false) in an LLM diff, that's the smell — "these booleans are unreadable at the call site and swap-prone; make them an enum or split the function."

The craft checklist — Bloch's maxims as review questions

  • Easy to use right, hard to use wrong. Is the correct call the obvious one? Can a plausible misuse even be written?
  • Least astonishment. Does it do what its name promises and nothing surprising?
  • No boolean traps. Any bare bool/magic flag that's opaque at the call site? Enum or split.
  • Argument order & consistency. Same idea in the same slot everywhere? (Kernel: handle first, data next, control/timeout last — across every queue function.)
  • Don't make the caller do what the API could. Push work down (lesson C15 / APoSD ch8).
  • When in doubt, leave it out. You can add to an API later; you can't remove. Small surface = deep module (lesson A2).

That's your API review checklist, captured as a durable reference: reference/api-review-checklist.html. Run it on the next interface you review and watch "this feels off" become a specific, quotable objection.

The strongest case against this brand of "craft"
  1. The dual interface fights "leave it out." Two functions per operation doubles the public surface — every reader learns xQueueSend and xQueueSendFromISR, ...Receive and ...ReceiveFromISR, and on. By A2's own logic, a bigger interface is shallower. So Bloch ("hard to misuse") and Ousterhout ("small surface") are in direct conflict here.
  2. Out-params are their own trap. pxHigherPriorityTaskWoken must be initialized, passed by address, and acted on later — easy to forget any step, and forgetting silently drops a context switch. "No boolean" traded one footgun for another.
  3. Consistency ossifies early mistakes. Once the ...FromISR + out-param convention is set across dozens of functions, it's unchangeable even if a cleaner design appears. Craft-as-consistency can lock in a mediocre local optimum forever (C11 blade 4: durability cuts both ways).

Synthesis. The conflicts are real, and resolving them is the judgment — the maxims are weights, not laws, and the tie-breaker is cost of misuse × frequency of misuse. On (1): the dual interface wins over "leave it out" precisely because the misuse it prevents (blocking in an ISR) is catastrophic and silent and the two contexts are genuinely different operations — so the extra surface buys a guarantee proportional to the danger. Where the two "contexts" were trivially similar and misuse was cheap, one function with a parameter would rightly win; you don't split abs() into absFromISR(). On (2): the out-param is justified by the same math — the ISR literally cannot yield inline (deep-dive), so some deferred-signal mechanism is unavoidable; the named pointer is the least-bad option, not a free win, and honest craft admits that. On (3): the durability that ossifies a convention is the same durability that makes a good convention compound — which is why C11 argued the type/API decision deserves the most review attention before it ships, because it's the one you can't cheaply take back. So craft isn't a checklist you pass; it's a set of forces you balance, weighted by how expensive and how likely each misuse is.

Module C, in one line Types are the review surface (C11) → hide behind opaque handles (C12) → make illegal states unrepresentable where misuse is silent and costly (C13) → assert the contracts types can't hold (C14) → design the errors away without losing observability (C15) → finish with craft, weighing the maxims by cost×frequency of misuse (C16). Six moves, one skill: read and shape an interface so the compiler, the caller, and the LLM all fall into the pit of success.
