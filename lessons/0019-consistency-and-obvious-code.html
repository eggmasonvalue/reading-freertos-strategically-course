Consistency is a force multiplier for the reader

Consistency lets a reader learn a pattern once and apply it everywhere, converting unknowns into knowns. It's the cheapest way to make a large codebase obvious — and a documented deviation is how you stay consistent while breaking a rule on purpose. But "a foolish consistency is the hobgoblin of little minds," so we'll find where consistency becomes a cage.

Why this lesson: This closes Module D and rhymes with A3: obvious code plus documented exceptions. It's also the perfect AI-era discipline — an LLM is a consistency-breaking machine (it averages over the world, not your repo), so "does this match how we already do it, and if not, is the exception recorded?" becomes one of your highest-frequency review questions. But applied dogmatically, consistency also blocks every improvement — so the skill is knowing when to break it.

The principle (APoSD ch17–18)

Ousterhout: consistency reduces cognitive load and unknown-unknowns — if similar things are done similarly, a reader relies on instincts instead of re-verifying each case.1 Code is obvious when a reader forms the right conclusion quickly, without much thought. Consistency is one of the biggest contributors to obviousness; surprising one-offs are one of its biggest enemies. The mechanism is specifically about the reader's prior: consistency lets them predict the unseen from the seen, and every violation silently poisons that prediction everywhere.

Specimen: how a safety-critical codebase records its exceptions

The kernel conforms to MISRA C:2012 — a strict, consistent rule set — but a small kernel sometimes must break a rule for footprint or performance. It never does so silently. In ./reference/FreeRTOS-Kernel/MISRA.md:

#### Dir 4.7
MISRA C:2012 Dir 4.7: If a function returns error information, then that
error information shall be tested.

_Ref 4.7.1_
 - taskENTER_CRITICAL_FROM_ISR returns the interrupt mask and not any error
   information. Therefore, there is no need to test the return value.

./reference/FreeRTOS-Kernel/MISRA.md — deviation records, lines 3–9 and 21–28

The pattern (you've seen its shape before) Every deviation carries three things: the rule broken, a grepable reference tag (Ref 4.7.1) that ties to the exact inline suppression in the source, and a justification. This is A3's objection → justification → evidence → escape hatch at codebase scale: the rule is the objection, the note is the justification, the Coverity tag is traceable evidence. Consistency isn't "never break the rule" — it's "break it only in the open, with a reason the next reader can find."

Why documented deviation beats both alternatives

Invert and look at the two failures it avoids. Silent deviation (break the rule, say nothing) destroys the reader's trust in the convention — now they must suspect every line, and the consistency is worthless everywhere, not just at the exception. Rigid conformance (never deviate) forces ugly or slower code to satisfy a rule that genuinely shouldn't apply here. The documented deviation keeps the value of consistency (readers still trust the rule holds unless a visible note says otherwise) while paying the real cost only at the one place it can't hold. That's mature engineering judgment made auditable — and it's the institutional version of the same move you make in a single well-commented line.

The strongest case against consistency
  1. "A foolish consistency is the hobgoblin of little minds." (Emerson.) Consistency with a bad pattern just propagates the mistake uniformly. Matching the surrounding code can mean copying its flaws — the codebase gets predictably wrong.
  2. It ossifies. Once a convention is everywhere, any improvement now creates an inconsistency, so the pressure is always to conform to the old way. Consistency becomes a ratchet that resists better ideas — the more consistent you are, the more expensive it is to improve.
  3. It can be cargo-culted. Enforcing "we always do X here" without knowing why X was chosen turns a once-reasoned convention into ritual — and rituals outlive the conditions that justified them.

Synthesis. Emerson's full quote is the key — a foolish consistency, not consistency as such — and the adjective is the whole judgment. Consistency's value is precisely measured: it's the amount of unknown it removes for the reader. So the decision rule follows directly: deviate when the value of the improvement exceeds the cost of the surprise it introduces — and when you do, document the deviation so the surprise cost drops toward zero. That reconciles both sides. Point (1): if the pattern is actively bad, the improvement's value is high and you should break it — but for the whole codebase in a migration, not as a lone one-off, because a single inconsistent fix pays the surprise cost without capturing the systemic value. Point (2): the ratchet is real, which is why deviations must be cheap to make legibly — a good deviation-record convention (like MISRA.md) is what keeps consistency from ossifying, because it lets you break the rule without destroying the reader's trust. Point (3): the antidote to cargo-cult is that every convention should have a recoverable rationale (A3 again) — so a reviewer can ask "why do we do X?" and get an answer, and retire X when its reason expires. So the mature stance isn't "be consistent" or "be free"; it's: consistency is the default because it removes unknowns; deviate deliberately when the improvement outweighs the surprise; and always leave a note, because a documented exception is what makes both consistency and change safe.

Red flag to name in reviews A one-off that departs from how the rest of the codebase does the same thing, with no note explaining why — the LLM special-casing something because it didn't look at the neighbors. Say it: "This breaks our established pattern. Either conform, or if the deviation is justified, record the reason where the next reader will find it — a silent exception erodes trust in the whole convention." And its inverse, so you're not a hobgoblin: "We're matching a pattern that's actually wrong here — if it's worth fixing, let's fix it codebase-wide and note the change, not conform to a mistake."
Module D, in one line Precise, consistent, honest names, split into the kind that carries meaning vs the kind that just restates the type (D17); comments that carry only what the code can't say, written first (D18); consistency as the unknown-removing default, with deliberate, documented deviations (D19). Readability isn't decoration — it's the interface between the code and every future reader, human or model. Obvious code is a strategic asset.
