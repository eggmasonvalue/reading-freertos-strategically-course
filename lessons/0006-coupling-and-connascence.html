Give the coupling a name

"This feels too coupled" is a vibe, and vibes lose arguments in review. Connascence is a 30-year-old taxonomy that turns that vibe into a precise noun — and a prescription. It's the sharpest single upgrade to the words you use in a PR.

Why this lesson: Ousterhout gives you deep vs shallow. Connascence (Page-Jones, Weirich) gives you a ruler for the dependencies themselves — which coupling is strong, whether its distance makes it dangerous, and exactly how to weaken it. That's the difference between "I don't like this" and "this is connascence of position across a boundary; here's the two-line fix." The second one an LLM can't argue with, and can be told to obey.

The idea: connascence = coupling you can rank

Two pieces of code are connascent if changing one forces a matching change in the other to keep the system correct.1 The taxonomy ranks the kinds by strength — how hard each is to refactor away — from the weakest (connascence of name) up through type, meaning, position, algorithm, and stronger still, the run-time (dynamic) forms. Two properties turn the rank into a decision:

  • Strength — weaker is cheaper to change. Prefer weaker forms.
  • Locality — strong coupling inside one small module is fine; the same strength stretched across a boundary is the problem. Distance raises the cost of strength.

The whole strategy compresses to one move: convert a stronger form into a weaker one, especially where it crosses a boundary. The full ranking, prescriptions, and Weirich's rules live in your new reference doc — the connascence cheat-sheet. Keep it open while you read.

What connascence does not claim. It is a ruler, not a commandment. It does not say all connascence is bad, or that you must drive it to zero — you can't; two pieces of code that must agree to be correct are connascent by definition, and a working system is full of necessary agreement. The claim is narrower and more useful: connascence tells you which coupling is strong and whether its distance makes that strength dangerous, so you know which one to weaken first. Strong connascence packed inside one small function is often perfectly fine (see the fold); the same strength stretched across a module boundary is the target. The taxonomy ranks priorities; it does not outlaw coupling.

Specimen A: connascence of position

Open ./reference/FreeRTOS-Kernel/include/queue.h. The workhorse send function:

BaseType_t xQueueGenericSend( QueueHandle_t xQueue,
                              const void * const pvItemToQueue,
                              TickType_t xTicksToWait,
                              const BaseType_t xCopyPosition );

./reference/FreeRTOS-Kernel/include/queue.h — lines 686–690

Four positional arguments. Every call site and the function must agree on the order: swap xTicksToWait and xCopyPosition in the signature and every caller silently breaks — both are integer-ish types, so the compiler may not even complain. That is connascence of position, and it lives across a module boundary (kernel ↔ every caller). By the cheat-sheet's ranking it's among the stronger static forms — precisely because there's no name to anchor the agreement, only a slot number.

The downgrade Position → Name. Passing a named struct ({ .queue=…, .ticks=…, .copyPosition=… }) replaces "agree on slot 3" with "agree on the field name copyPosition" — connascence of name, the weakest form. C's ergonomics push APIs toward positional args, so this trade-off is a genuine judgment call — but naming why you tolerate it is the strategic act.

Specimen B: connascence of meaning — and the kernel fixing it

Now the good-citizen half. A queue's "send to front or back?" could have been a raw 0/1 that caller and kernel both secretly know — classic connascence of meaning (a magic value two sides must interpret identically). Instead, in projdefs.h and queue.h:

/* projdefs.h & queue.h — meaning turned into name */
#define pdPASS               ( pdTRUE )            /* not a bare 1 */
#define pdFAIL               ( pdFALSE )           /* not a bare 0 */
#define queueSEND_TO_BACK    ( ( BaseType_t ) 0 )
#define queueSEND_TO_FRONT   ( ( BaseType_t ) 1 )

./reference/FreeRTOS-Kernel/include/projdefs.h — lines 52–60; include/queue.h — lines 68–69

By giving the magic values names, the kernel deliberately performed the cheat-sheet's headline move: meaning → name. A caller writes queueSEND_TO_FRONT, not 1; nobody has to remember that 1 means front. This is the same instinct as the whole codebase — the Hungarian prefixes, the opaque handles — turned on a humble constant. Seeing that the kernel does this on purpose is the lesson: strong coupling isn't fate, it's a thing you actively weaken.

Specimen C: connascence of algorithm (the one to watch)

The ...FromISR functions take a BaseType_t *pxHigherPriorityTaskWoken. The contract, from the header:

"…will set *pxHigherPriorityTaskWoken to pdTRUE if sending caused a higher-priority task to unblock. If it sets this to pdTRUE then a context switch should be requested before the interrupt is exited."

./reference/FreeRTOS-Kernel/include/queue.h — lines 996–999

That is a shared protocol the ISR author must execute in step with the kernel: initialise the flag to pdFALSE, pass its address, then after the call, if it's pdTRUE, request a yield. Caller and kernel are connascent on an algorithm — the strongest static form on the sheet, and it's spread across every ISR that touches a queue (high degree, long distance). The kernel accepts this cost for real-time reasons, and it pays it down the only way you can: by documenting the protocol precisely at the interface (your Lesson 3 skill), so the shared algorithm is at least legible.

Deep dive — static vs dynamic connascence, and why the ISR dance is the scary kind

The cheat-sheet splits connascence into static forms (visible in the source text — name, type, meaning, position, algorithm) and dynamic forms (only manifest at run time — execution order, timing, value, identity). Dynamic is worse for one mechanical reason: a static agreement can be checked by reading or by the compiler; a dynamic one can only be caught by running the exact interleaving that violates it. The ...FromISR contract is really connascence of execution order (you must yield after the call, not before) layered on connascence of algorithm — which is why it's the most dangerous coupling in the whole lesson: get the order wrong and it compiles, passes most tests, and drops a context switch only under load. The kernel can't downgrade it (real-time constraints make the protocol essential), so it does the next best thing — converts as much as possible to static, legible form: a named out-parameter, a precise header contract, and configASSERTs that turn some runtime violations into loud early failures (lesson C14). When you can't remove strong connascence, make it as static and local as the problem allows.

The strongest case against connascence-talk (steelman)

An experienced reviewer might roll their eyes at the vocabulary. Steelman that reaction, then synthesise.

The case against
  1. It's jargon for what we already have. "Coupling" and "cohesion" have covered this for fifty years. Renaming "passing too many positional args" as "connascence of position" adds Latin, not insight.
  2. The taxonomy is over-precise. Arguing whether something is connascence of meaning vs. algorithm is angels-on-a-pin — it doesn't change what you actually do to the code.
  3. The prescriptions fight the language. "Downgrade position to name" means named-parameter structs — but C's ergonomics push hard toward positional args, so the advice is unusable where you most need it (systems C).

The synthesis. The steelman is right that connascence refines coupling rather than replacing it — but that refinement is exactly the value, and it's the difference between losing and winning a review. "This feels too coupled" is a vibe the author can wave off; "this is connascence of position across a module boundary, and the fix is a named struct" is a ranked, located, prescriptive claim they have to engage with (that's point 1 conceded and turned around). Point (2) is fair as a caution: the label matters only insofar as it changes the strength and therefore the priority — don't argue meaning-vs-algorithm for sport, argue it when it decides what to weaken first. Point (3) is the sharpest and the lesson already concedes it: C does push toward positional args, which is why the strategic act often isn't to eliminate the connascence but to name it and justify tolerating it — an explicit "we accept connascence of position here because C, and we contain the blast radius with asserts and a tight contract" is a real design decision, not a failure. The taxonomy's job is to make that decision sayable.

Munger inversion — hunt the coupling the compiler can't see Don't ask "is this well-decoupled?" — invert it: "if I changed this, what elsewhere would have to change in lockstep, and would anything tell me if I forgot?" The couplings that will kill you are the ones with no machine check: two same-typed positional args you can swap silently, a bare 1 both sides must interpret, an out-parameter protocol you must run in the right order. Weak connascence (name, type) is mostly caught by the compiler; strong connascence across a boundary is caught by nobody — which is precisely why the taxonomy ranks it worst and why that's where you spend your review attention.
Red flag to name in reviews A function with several same-type positional args (position); a bare 2 or -1 whose meaning both sides must know (meaning); a "call these in this exact order" out-parameter dance (algorithm/execution) — especially when the two parties sit in different modules. The words: "That's connascence of ___ across a boundary. Downgrade it: name the constant / pass a struct / encapsulate the protocol." LLMs generate all three of these by default, because each is locally convenient.
