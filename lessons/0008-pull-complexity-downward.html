Strategic Programmer / Lesson 08 / ~13 min / Module B

Someone has to eat the complexity

Complexity in a system is conserved — it doesn't vanish, it only moves. The one real choice a designer makes is where it lands: inside the module, paid once by its author, or out in the interface, paid forever by every caller. Ousterhout's Ch. 8 gives the default direction, and it's counter-intuitive: pull it down.

Why this lesson: An LLM optimises for a module that's easy to write, not one that's easy to use — so it reflexively pushes complexity up: extra parameters "for flexibility", config flags, an init() you must remember to call, a mode you must set first. Each one looks harmless in the diff and taxes every future caller. This lesson trains you to see the direction complexity is flowing and to push back: make the module suffer so the caller doesn't.

The idea: a simple interface beats a simple implementation

Ousterhout's Ch. 8: when you must choose, it is more important for a module to have a simple interface than a simple implementation.1 A module is written once and used many times; the interface is paid by everyone, the implementation only by its author. So when there's ugliness to absorb, the module developer should take it on internally — pull complexity downward — rather than exposing it and letting it "become someone else's problem." The tell that you're doing it wrong: a new configuration parameter, or a caller-facing flag, that exists only because handling the case inside the module felt harder.

What this does not claim. "Pull down" is a default with conditions, not "hide everything inside." Ousterhout's own three conditions: pull complexity down when it's closely related to the module's existing function, when doing so simplifies many callers, and when it genuinely shrinks the interface. Absorb complexity that fails those — unrelated concerns, a case only one exotic caller hits, ugliness that doesn't actually simplify the interface — and you've just built a kitchen-sink module that's a nightmare inside and no simpler outside. The claim is directional (prefer down), bounded by "and only when it buys a simpler interface for real callers."

down good

The mess lives inside the implementation. The interface stays two functions wide. The author suffers once; every caller is spared. Cost is paid at the narrowest point.

up costly

The mess is exported as parameters, flags, ordering rules, "call this first." The author saved an afternoon; every caller pays the tax forever. A shallow module by construction.

Specimen A: five heaps, one door

Dynamic allocation is genuinely hard on an embedded target: fragmentation, coalescing freed blocks, alignment, thread-safety, determinism. FreeRTOS could have surfaced those choices to you. Instead the entire caller-facing interface is two functions, declared once in portable.h:

/* portable.h — the whole public surface of memory management */
void * pvPortMalloc( size_t xWantedSize );
void   vPortFree( void * pv );

./reference/FreeRTOS-Kernel/include/portable.h — lines 189, 192

Behind that unchanging door sit five complete, swappable implementations in portable/MemMang/, each absorbing a different amount of ugliness so you don't have to:

  • heap_1.c (178 lines) — allocate-only, never frees. Tiny, deterministic, safety-critical friendly.
  • heap_2.c (407 lines) — frees, best-fit, but doesn't coalesce. Kept for legacy.
  • heap_3.c (106 lines) — a thin, thread-safe wrapper over the compiler's own malloc/free, guarded by suspending the scheduler.
  • heap_4.c (638 lines) — best-fit with coalescence of adjacent free blocks, to fight fragmentation. The workhorse.
  • heap_5.c (756 lines) — heap_4 plus the ability to span multiple non-contiguous memory regions.

Look at what heap_4 quietly does on your behalf — its header states the contract:

/*
 * A sample implementation of pvPortMalloc() and vPortFree() that combines
 * (coalescences) adjacent memory blocks as they are freed, and in so doing
 * limits memory fragmentation.
 */

./reference/FreeRTOS-Kernel/portable/MemMang/heap_4.c — lines 29–35

Verdict Coalescence, best-fit search, block-link bookkeeping, alignment, thread-safety — hundreds of lines of it — are pulled down below a two-function interface. You choose your allocator once, by linking one .c file, and then never think about it again: your call site is always pvPortMalloc( n ). The complexity didn't disappear; it was moved to the narrowest, cheapest place to pay for it — and made a variation seam so a project can trade determinism for anti-fragmentation without touching a single caller.

Specimen B: xTaskCreate swallows the stack-growth mess

Creating a task means allocating a TCB and a stack, zeroing them, and laying the stack out correctly — and stacks grow up on some CPUs and down on others. That last detail is exactly the kind of hardware ugliness that tempts a designer to make it the caller's problem. prvCreateTask (the guts of xTaskCreate) refuses, and forks internally instead:

/* tasks.c — the same job, two orderings, decided by the port, hidden from you */
#if ( portSTACK_GROWTH > 0 )
    /* stack grows up: TCB first, then stack */
    pxNewTCB->pxStack = pvPortMallocStack( uxStackDepth * sizeof( StackType_t ) );
#else
    /* stack grows down: stack first, then TCB */
    pxStack   = pvPortMallocStack( uxStackDepth * sizeof( StackType_t ) );
    pxNewTCB  = pvPortMalloc( sizeof( TCB_t ) );
    ( void ) memset( pxNewTCB, 0x00, sizeof( TCB_t ) );
#endif

./reference/FreeRTOS-Kernel/tasks.c — prvCreateTask, lines 1631–1726; the portSTACK_GROWTH fork is at lines 1643–1710

The interface you actually touch stays serene — xTaskCreate( fn, name, stackDepth, param, prio, &handle ). You pass a stack depth, a plain number; the module eats the allocation, the ordering, the zeroing, and the CPU-specific direction. That is complexity pulled downward until the caller sees a flat, obvious call.

The honest borderline: when you push complexity up on purpose

"Pull down" is a default, not a commandment — and FreeRTOS itself breaks it, deliberately, with a straight face. Alongside xTaskCreate lives xTaskCreateStatic:

/* task.h — the caller must now supply the memory themselves */
TaskHandle_t xTaskCreateStatic( TaskFunction_t pxTaskCode, ...,
                                StackType_t  * const puxStackBuffer,
                                StaticTask_t * const pxTaskBuffer );

./reference/FreeRTOS-Kernel/include/task.h — lines 523–529

This shoves real complexity up: now you must declare and own the stack buffer and the TCB buffer and keep them alive for the task's whole life. Why is that not the exact anti-pattern we just condemned? Because an external force demands it: safety-critical and MISRA-constrained builds forbid dynamic allocation outright (configSUPPORT_DYNAMIC_ALLOCATION 0). When the heap is off the table, the memory has to come from the caller — the complexity is real and irreducible, not manufactured laziness. Two things make the push-up honest rather than a leak:

  • It's a separate, explicitly named interface (...Static), not extra parameters bolted onto the simple one. The caller opts in, eyes open.
  • It exists only because a genuine constraint (no heap) makes pulling-down impossible — not because absorbing it was merely inconvenient.
Munger inversion — know where the rule dies Invert the principle to find its edge: you may push complexity up only when (1) the complexity is essential and cannot be hidden without lying, and (2) an outside constraint — not your own convenience — forces the caller to own it. The instant "it was hard to handle inside" is the real reason, you've mislabelled laziness as flexibility. FreeRTOS passes both tests; the LLM's spurious config flag passes neither.
Deep dive — the second-order cost: pulling down concentrates complexity (and hiding can be a lie)

Pulling complexity down doesn't destroy it — it concentrates it in one place, and that has two consequences worth naming. First, the module author now carries the hardest part of the whole system, so the deepest modules demand your best engineering and your most careful review — heap_4.c's coalescing allocator is 638 lines because it ate fragmentation on everyone's behalf; a bug there is a bug everywhere. Concentration is the right trade (one hard place beats a thousand easy-but-wrong call sites), but it means "deep" and "low-risk" are not synonyms — depth moves risk to where it can at least be reviewed once. Second, the honest limit: hiding is a lie when the thing you hid is something the caller genuinely needed to decide. Bury a heap allocation inside a function called on a real-time deadline and you've hidden a decision ("this can block / can fail / can fragment") that the caller had every right to see — which is exactly why FreeRTOS doesn't hide it under configSUPPORT_DYNAMIC_ALLOCATION 0, and exposes xTaskCreateStatic instead. The test for "is this hiding or lying?" is: would a competent caller be surprised, and harmed, to learn what I hid?

The strongest case against pulling down (steelman)

The opposite instinct — expose the knobs, let the caller decide — has real force. State it well, then synthesise.

The case against
  1. Absorb-everything modules rot. Every case you pull inside makes the implementation bigger and more conditional. Push far enough and you get a 5,000-line god-module with twelve internal modes — simple interface, unmaintainable guts. The complexity didn't leave; it metastasised.
  2. The author can't know all callers. A library author who hides a decision robs a caller with different needs of control. Exposing the knob is humility — it admits you can't predict every use, so you let the person who knows their case choose.
  3. Hidden complexity is un-tunable. When performance matters, a caller needs to reach the allocation strategy, the buffer size, the retry policy. A too-simple interface makes the module a black box you can't optimise through.

The synthesis. Each point marks a real boundary of the rule rather than breaking it. Point (1) is why the rule is conditional: pull down only complexity related to the module's function — an allocator absorbing allocation concerns stays cohesive; an allocator that also grew a logging framework and a config parser is the god-module, and the fix is to split by secret (lesson B10), not to push the allocation back up. Points (2) and (3) are the same true observation — sometimes the caller must decide — and FreeRTOS's answer is the pattern to copy: don't bolt a knob onto the simple interface, offer a separate, honestly-named one (...Static, or the five linkable heap_*.c files). The caller who needs control opts into it, eyes open; the 95% who don't keep pvPortMalloc(n). So the honest position isn't "hide maximally" — it's "hide the related complexity behind the simplest interface that doesn't lie, and expose genuine caller-decisions as separate opt-in interfaces, never as flags on the easy path."

Red flag to name in reviews A new parameter, flag, mode, or "call init() first" that exists to make the implementation easier, taxing every caller to save the author once. The words: "This pushes complexity onto every caller to keep the module simple inside — the tradeoff runs the wrong way. What forces the caller to own this, versus us absorbing it below the interface?" If the honest answer is "nothing, it was just easier to write this way," pull it back down.
