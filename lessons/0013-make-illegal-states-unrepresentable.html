The bug the type won't let you write

The most powerful thing a type can do is not describe a value but make a whole category of wrong values impossible to construct. This lesson shows the ideal, proves exactly where C — and FreeRTOS — cannot reach it, and prices the deliberate hole that trade left behind.

Why this lesson: "Make illegal states unrepresentable" is the maximal form of C11's constrain the generator: a program an author cannot express is a program you never have to review. But C's type system is weak, and today's specimen contains a real, intentional hole. Seeing the hole — understanding the exact language rule that opens it, and pricing what was bought — is the enrich-tier skill. This is a Munger lesson: study where C dies so you never rely on it there.

The principle — and its precise scope

Type-driven design (Alexis King, "Parse, Don't Validate")1: rather than accept a loose value and check it at every use, accept a narrower type that can only hold valid values, and validate once — at construction — turning the checked value into a type that proves its own validity thereafter. The illegal state then has no representation: it is not "caught," it is uninstantiable.

Scope it honestly, though: this is a spectrum, not a binary, and how far you can travel depends on the language. A strong sum-type language reaches near the ideal; C reaches part way and must back the rest with runtime checks. The skill is knowing exactly how far your language goes.

The map of the walls (Munger: study the far end so you can navigate the near one) In a strong-typed language you write the walls directly. A sum type says "exactly one of these, never two, never none," and a newtype makes look-alikes distinct: 
// Rust — a value that is a queue XOR a semaphore, never confusable
enum Primitive { Queue(Queue), Semaphore(Semaphore) }
// and the compiler forces you to handle BOTH arms — exhaustively:
match p { Primitive::Queue(q) => ..., Primitive::Semaphore(s) => ... }
// distinct newtypes: a Receiver<T> simply is not a Sender<T>.
You are not being told to switch languages. You are being handed a map: this is the guarantee — construction-checked validity, exhaustiveness, nominal distinctness — so you can recognize precisely which piece you must hand-build when you're in C, and which piece C simply will not give you.

Specimen: where FreeRTOS deliberately leaves a wall down

Open ./reference/FreeRTOS-Kernel/include/semphr.h and include/queue.h:

/* semphr.h */
typedef QueueHandle_t SemaphoreHandle_t;              /* line 38 */

/* queue.h — all of these are the SAME type */
typedef struct QueueDefinition * QueueHandle_t;         /* 51 */
typedef struct QueueDefinition * QueueSetHandle_t;       /* 58 */
typedef struct QueueDefinition * QueueSetMemberHandle_t; /* 65 */

./reference/FreeRTOS-Kernel/include/semphr.h — line 38

./reference/FreeRTOS-Kernel/include/queue.h — lines 51, 58, 65

The exact C rule that makes this a hole typedef introduces an alias, not a new type. After typedef QueueHandle_t SemaphoreHandle_t; the two names denote the same type; C compares them structurally and finds no difference. So this compiles with no diagnostic: 
SemaphoreHandle_t s = xSemaphoreCreateBinary();
xQueueSend( s, &data, 0 );   /* sending DATA to a semaphore — nonsense, accepted */
The illegal state — "treat this semaphore as a data queue" — is fully representable. The type system offers no wall here at all.
Deep dive — name equivalence vs structural equivalence (the jagged corner)

C uses structural equivalence for typedef aliases (same underlying type ⇒ same type) but name/tag equivalence for struct, union, and enum tags: two structs with identical members but different tags are distinct types. That single asymmetry is the entire basis of the C99 fix below — it's why wrapping a value in a fresh struct buys you a genuinely new type while a typedef never can. Most C developers carry a fuzzy sense that "typedef makes a type"; it does not, and knowing the difference precisely is what lets you reach for the struct-wrapper deliberately instead of hoping an alias will protect you. (This is on your list of jagged corners — worth over-learning.)

Why the hole is there — and why it's a fair trade

This is not sloppiness; it is the flip side of a decision you already admired. In lesson A2 a semaphore is a queue — one deep implementation reused four ways — and that reuse is bought by collapsing the handle types into one. FreeRTOS chose: maximal implementation reuse and a tiny public surface, at the cost of compile-time distinctness between handle kinds.

Then — and this is the part the batch version glossed — it buys some of the safety back at runtime. The hidden struct carries a ucQueueType field and a uxItemSize, and the semaphore entry points assert on them. Verified, in queue.c:

/* xQueueSemaphoreTake — a semaphore stores zero-size items */
configASSERT( pxQueue->uxItemSize == 0 );                /* line 1355 */
/* xQueuePeekFromISR */
configASSERT( pxQueue->uxItemSize != 0 );  /* line 2150: "Can't peek a semaphore." */

./reference/FreeRTOS-Kernel/queue.c — lines 1353–1355, 1672–1677, 2147–2150

The full, honest picture The guarantee didn't vanish; it moved layers. What a strong type system would enforce at compile time, always, FreeRTOS enforces at runtime, only when configASSERT is enabled (lesson C14). A strategic reviewer states both halves in one breath: "the handle types are unified for reuse; distinctness is recovered at runtime via uxItemSize/ucQueueType asserts — so on a release build with asserts off, misusing a semaphore as a queue is undefined behavior with no diagnostic at all." That sentence is the whole lesson: know which wall exists, at which layer, under which build.

What you hand-build in C99 when you do want the compile-time wall

When distinctness matters more than reuse, C's escape hatch is the struct-wrapper newtype — legitimate precisely because of the tag-equivalence rule in the deep-dive above:

/* Give each handle kind its own real, distinct type */
typedef struct { QueueHandle_t h; } SemHandle_t;
typedef struct { QueueHandle_t h; } DataQueue_t;

/* The "parse" boundary: the ONLY way to make one is a checked constructor */
SemHandle_t SemCreate( void ) { SemHandle_t s = { xSemaphoreCreateBinary() }; return s; }

void give( SemHandle_t s );
give( myDataQueue );   /* ERROR: incompatible type. The wall is back. */

Combine the wrapper (nominal distinctness) with the opaque-handle move from C12 (hide the field so callers can't unwrap it), a constructor as the single validated entry (King's "parse" step), and configASSERT for the invariants the type still can't state — and you have reconstructed, by hand and on purpose, most of what a sum type would have given you free. That layering is the C craft: the type carries what it can, the constructor validates once, the assert covers the remainder.

The strongest case against "make it unrepresentable" (in C)
  1. Wrapper friction is real. Every struct-newtype means wrapping/unwrapping at boundaries, more constructors, and uglier call sites. In C the ergonomics are bad enough that the safety can cost more reading clarity than it buys.
  2. C can't reach the valuable part anyway. Nominal distinctness is the easy win; C gives you no sum types, no exhaustiveness checking, no non-null-by-construction. So you do the work and still can't express the states that actually matter — a runtime check would have covered more, for less.
  3. FreeRTOS's own choice argues against you. The most-used embedded kernel in the world looked at exactly this tradeoff and chose the unified type plus runtime asserts. If unrepresentability were obviously right here, they'd have wrapped.

Synthesis. The steelman is strong and it correctly bounds the technique — but it argues for judgment, not abstention. Point (2) is the real key: in C, reach for the compile-time wall only where nominal distinctness alone kills a real, costly, silent bug (mixing a raw and a sanitized string; a user-id and an account-id; a physical and a virtual address) — cases where a swap compiles, runs, and corrupts quietly. Where the meaningful illegal states are richer than "wrong nominal type," accept that C dies there and back it with configASSERT (C14) — which is exactly what FreeRTOS did, deliberately, and could state the reason for. The wrong move isn't choosing runtime checks; it's choosing them by default without knowing you had a compile-time option and declining it on purpose.

Red flag to name in reviews Two conceptually different things sharing one typedef alias where swapping them would be a silent bug — a "user id" and an "account id" both bare uint32_t, a sanitized and a raw string both char *. Say it: "These are the same type to the compiler, so it will happily let us swap them — an illegal state we've left representable. If the mix is a real, silent bug, wrap each in its own struct; if not, don't pay the wrapper tax." LLMs alias types constantly (they average over code that does); this is a standing review move — applied with the proportionality the steelman demands.
