Strategic Programmer / Lesson 09 / ~13 min / Module B

Draw the line where the change will fall

Every codebase has a fault line: the set of things that will change — this chip, that tick rate, whether mutexes are even compiled in. A design either gathers those changes behind one seam, or scatters them through the source as landmines. Parnas's 1972 insight is that you can predict the fault line and build the seam first.

Why this lesson: The most expensive review miss isn't a bug — it's a decision that's smeared across fifty files, so that changing it later means fifty edits and one forgotten. LLMs produce this constantly: a magic number inlined everywhere, a platform assumption baked into each function, a feature you can't remove because it has no boundary. This lesson trains you to ask of any likely-to-change fact: does this live in exactly one place? — and to design that one place on purpose.

The idea: encapsulate the decisions likely to change

Parnas, On the Criteria To Be Used in Decomposing Systems into Modules (1972): don't split a system by the steps it performs — split it by the design decisions that are likely to change, and hide each one inside a module so that a change touches that module only.1 Ousterhout gives the same idea a sharper edge in the design vocabulary you already own: a change that's isolated is a deep boundary paying off; a change smeared across modules is information leakage — the same secret known in many places. The strategic act is to name the thing that varies and give it a seam before the variation arrives.

seam good

Everything that varies — tick width, heap choice, which features exist — is pulled to one boundary. To retarget the system you edit one place. The rest of the kernel never learned the secret.

smear costly

The same changeable fact — a constant, a platform assumption — is copied into every file that needs it. Changing it is a search-and-replace across the tree, and the one you miss is the bug.

Specimen: FreeRTOSConfig.h as the system's fault line

FreeRTOS runs on dozens of chips, in 16- or 32- or 64-bit tick widths, with or without mutexes, timers, or dynamic allocation — an enormous space of variation. Almost none of that variation lives in the kernel source. It's gathered into one file the application owns, pulled in before anything else compiles:

/* FreeRTOS.h — the very first thing the kernel does is ask you for the secrets */
/* Application specific configuration options. */
#include "FreeRTOSConfig.h"

./reference/FreeRTOS-Kernel/include/FreeRTOS.h — line 58

Roughly 100 distinct config* / INCLUDE_* macros are read across the kernel, and every one of them resolves at this single seam. The kernel body never says "assume 32-bit ticks" or "assume mutexes exist" — it asks the seam. Three moves make the seam load-bearing rather than decorative:

1. Sensible defaults, provided centrally

Right after including your config, FreeRTOS.h fills every gap you left, so the kernel body can assume every macro is defined:

/* FreeRTOS.h — "if the app didn't decide, here's the safe default" */
#ifndef configUSE_MUTEXES
    #define configUSE_MUTEXES        0
#endif
#ifndef configUSE_TIMERS
    #define configUSE_TIMERS         0
#endif
#ifndef INCLUDE_vTaskDelete
    #define INCLUDE_vTaskDelete      0
#endif

./reference/FreeRTOS-Kernel/include/FreeRTOS.h — lines 226–228, 330–336

2. The seam validates itself

Some decisions must be made, or make no sense in combination. The seam refuses to compile rather than silently guess — pushing errors to build time, where they're cheapest:

/* FreeRTOS.h — a missing or contradictory decision fails loudly, early */
#if !defined( configUSE_16_BIT_TICKS ) && !defined( configTICK_TYPE_WIDTH_IN_BITS )
    #error Missing definition: One of configUSE_16_BIT_TICKS and
           configTICK_TYPE_WIDTH_IN_BITS must be defined in FreeRTOSConfig.h.
#endif

./reference/FreeRTOS-Kernel/include/FreeRTOS.h — lines 60–62

3. Whole features vanish through the seam

Because the macro is known in one place, a feature can be compiled out entirely — not just disabled at runtime. Set INCLUDE_vTaskDelete to 0 and the function isn't merely unreachable, it doesn't exist:

/* tasks.c — the whole implementation is fenced by the seam's macro */
#if ( INCLUDE_vTaskDelete == 1 )
    void vTaskDelete( TaskHandle_t xTaskToDelete ) { /* ...200 lines... */ }
#endif

./reference/FreeRTOS-Kernel/tasks.c — lines 485–490 and 626–630

Verdict The likely-to-change facts of an RTOS — word size, feature set, allocation policy, assert strategy — are named as config* macros and gathered at a single, self-validating, self-defaulting seam. To retarget FreeRTOS you edit one file you own; the ~10k lines of kernel never change. That's Parnas exactly: the module boundary is drawn around what varies, not around what the code does step by step. The seam is the product's portability.
Deep dive — the seam has its own cost: #ifdef combinatorics, and why the #errors exist

Isolating change through config* macros is not free, and a strategic reader should see the bill. ~100 boolean-ish knobs define, in principle, an astronomical number of build configurations — and #if-fenced code is only compiled in the configs that enable it, so a combination no one built is a combination no one type-checked. This is the real reason the kernel body is dense with #if ( INCLUDE_x == 1 ) fences and the header front-loads dozens of #error guards: the guards prune the invalid region of the configuration space at build time, converting "silently broken combination" into "won't compile, here's why." That's the second-order insight — the self-validation you saw in move 2 isn't politeness, it's the containment that makes a 100-knob seam tractable instead of a combinatorial minefield. The general lesson: when you create a variation seam, you also inherit responsibility for the cross-products of its options, and the cheapest way to discharge that is to make illegal combinations fail loudly and early (a preview of lesson C14's build-time and run-time asserts, and of C13's "make illegal states unrepresentable").

The strongest case against building seams (steelman)

Emergent-design advocates would push back hard on "design the seam first." State their case at full strength, then synthesise.

The case against
  1. You can't predict change. Every seam encodes a guess about what will vary. Guess wrong — as teams usually do — and you've paid for flexibility along an axis nothing moves on, while the change that does come cuts across your seams. Simpler to write plainly and refactor when reality arrives (YAGNI / emergent design).
  2. Seams are complexity. ~100 macros is #ifdef soup: code that reads differently per build, paths you can't see without knowing the config, a combinatorial test burden. The abstraction meant to tame change becomes its own source of cognitive load.
  3. Refactoring is cheap now. With modern tooling, extracting a seam when the second case appears is a small, safe change — so pre-building it buys little and risks freezing the wrong boundary.

The synthesis. The steelman is correct as a default — and the lesson already conceded it: speculative seams are the over-engineer's trap, and "the discipline is prediction, not paranoia." The resolution is that Parnas's rule and YAGNI agree far more than they look. Both say: don't build a seam for a change you're guessing at. They differ only on changes you can demonstrate. FreeRTOS didn't speculate that it might someday run on another chip — portability across architectures is its entire reason to exist, an observed, recurring variation, so its seams sit on fault lines that provably move. That's the test that separates a good seam from #ifdef soup: is there real, occurring variation along this axis, or am I imagining one? Point (3) is the tie-breaker for genuine uncertainty — when you're not sure the change will come, YAGNI wins, because refactoring-in a seam later is cheap and un-building a wrong one is not. So: seam the changes you can point to; write plainly and wait on the ones you can only imagine.

The honest borderline: don't build seams for changes that won't come

The failure mode isn't only too few seams — it's too many. A config knob, a strategy interface, or a plugin point built for a variation that never arrives is pure cost: it enlarges the interface (shallower module), and every reader now has to reason about a flexibility no one uses. FreeRTOS earns its ~100 macros because each corresponds to a variation that demonstrably occurs across real ports and real products. The discipline is prediction, not paranoia.

Munger inversion — where the rule dies Invert "isolate what changes" and you get its two failure modes at once: (1) you failed to predict a real change, so it's smeared everywhere (the common one) — and (2) you predicted a change that never came, so you paid for a seam that only adds interface (the over-engineer's trap). A good seam sits exactly on a fault line that will move. Speculative generality is just leakage with better manners.
Red flag to name in reviews A changeable fact — a platform constant, a tuning number, a feature toggle — appearing in more than one file. The words: "This decision is duplicated across N sites; the day it changes, one of them will be missed. Give it a single owner — a named constant or a config seam — and have everything ask that." And its mirror, aimed at over-eager models: "What real, occurring variation is this configuration point for? If none, delete it — the flexibility is costing us and buying nothing."
