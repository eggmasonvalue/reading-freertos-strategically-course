The signature is the spec

Module C is your named priority, so it opens with its own thesis and then earns it. The claim: of everything you can review, the type signature gives the highest return on a reviewer's scarcest resource — attention. This lesson makes that argument rigorously, states exactly what it does not claim, and steelmans the case against it.

Why this lesson: "The models slopify my types and abstractions." If types are where the slop lands, they're also where you stop it — but only if you can say why the type is the leverage point, not just assert it. Everything later in Module C (opaque handles, illegal states, contracts, error design, API craft) is an application of the argument built here. Get the thesis wrong and the whole module is cargo-cult.

First, the claim — stated precisely, with its limits

The thesis is a claim about marginal return on reviewer attention, not about correctness or omnipotence. Precisely:

Per unit of a reviewer's finite attention, examining the type signatures of a change yields more design information — and more enforced constraint on both human and machine authors — than examining any other single surface (bodies, tests, comments, commit messages).

Note what this deliberately does not say. It does not say types catch most bugs (they don't — see the steelman below). It does not say a program is correct because it type-checks. It says: if you have ten minutes and must spend them on one surface, the signatures are where the marginal minute buys the most. Hold that scope; the whole lesson defends that sentence and nothing larger.

Specimen: a reviewer's line-by-line read

Open ./reference/FreeRTOS-Kernel/include/task.h. Two declarations — the handle (lines 98–100) and the constructor (lines 395–402):

typedef struct tskTaskControlBlock * TaskHandle_t;

BaseType_t xTaskCreate( TaskFunction_t          pxTaskCode,
                        const char * const       pcName,
                        const configSTACK_DEPTH_TYPE uxStackDepth,
                        void * const              pvParameters,
                        UBaseType_t             uxPriority,
                        TaskHandle_t *          const pxCreatedTask );

./reference/FreeRTOS-Kernel/include/task.h — lines 98–100 and 395–402

Now read it the way a strategic reviewer does — every token is a decision you can interrogate:

  • TaskHandle_t is a pointer to a struct you were never given the definition of (lesson C12). Design decision, visible in the type: the task's internals are hidden and you may not touch them.
  • const char * const pcName — two consts. The first: the function won't mutate the string. The second: it won't reassign the pointer. A reviewer infers a lifetime intent — the name is borrowed, read-only — without opening the body.
  • const configSTACK_DEPTH_TYPE uxStackDepth — the stack size is a configurable width, not a hardcoded int. That single token tells you the kernel is portable across 16- and 32-bit targets (lesson B9's variation seam), surfaced in a signature.
  • void * const pvParameters — an escape hatch: the kernel deliberately does not know your parameter's type. That's a real design tradeoff (flexibility bought with a hole in type safety — the exact hole lesson C13 studies).
  • TaskHandle_t * const pxCreatedTask as the last parameter, with BaseType_t returned — the return channel is pass/fail, the out-parameter is the result. A convention you can now check at every call site in the codebase.
  • Return BaseType_t, not void — creation can fail (out of heap), and the type forces the caller to have somewhere to notice (lesson C15). A void here would have hidden a failure mode.
What just happened You reconstructed six independent design decisions — information hiding, borrowing semantics, portability, a deliberate type hole, a calling convention, and a failure contract — in about the time it takes to read the signature. You have not read one line of tasks.c. That density is not a nicety; it is the entire argument, and the four blades below just name why it holds.

The four blades — each with its mechanism

1. Review density — an information-theoretic claim

Ousterhout defines a module's interface as "everything a developer must know to use it."1 A signature is the maximally compressed encoding of that knowledge: it states the contract in the fewest tokens the language permits, and — crucially — in a form the reader is already fluent in. Six parameters above encoded what English would need three paragraphs to say. Because a reviewer's attention is finite and roughly constant per token, the surface with the highest design-facts-per-token is the surface with the highest return per minute. The signature is that surface by construction — it is the compression of the contract.

Deep dive — the second-order effect on where you spend attention

There's a compounding consequence. Because signatures are dense and bodies are sparse, attention spent on signatures scales sub-linearly with codebase size — you can review the public interface of a 10k-line kernel in an afternoon, but not its bodies. So as systems (and LLM output) grow, the relative value of interface review rises: it's the only review that stays tractable at scale. This is why senior reviewers gravitate to "let me see the headers first" — not taste, but the math of bounded attention against unbounded code. It also predicts a failure mode: a reviewer who reads bodies first burns their budget before reaching the surface that would have told them the most.

2. It constrains the generator — a compile-time claim, not a review-time one

This is the blade most people miss, and it is the AI-era crux. A type is not only something a reviewer reads; it is something that acts before and during generation. Give an author — human or model — the type TaskHandle_t, and they cannot hand you a raw int, cannot dereference the TCB, cannot pass a queue where a task is wanted: the compiler removes those programs from the space of things that will build. A prose instruction ("please keep the handle opaque") is a request evaluated by a fallible reader. A type is a wall evaluated by a machine. The difference is enforcement location: prose is honored at the author's discretion; a type is honored by cc.

The inversion that reframes the AI era The lazy take: "LLMs write the code now, so craft and types matter less." Invert it. When generation becomes cheap and abundant, the scarce, valuable things are (a) constraints that prune bad generations automatically and (b) review surfaces that stay tractable against a flood of output. A type is both. So the correct conclusion is the opposite of the lazy one: the cheaper generation gets, the more valuable the type system becomes, because it's the machine that says "no" without spending your attention. That is why types are Module C's thesis and not a footnote.

3. It's the only machine-checked contract — argued against the alternatives

Four things claim to record a contract; only one is verified on every build. Take them in turn, honestly:

  • Comments rot, because nothing forces them to agree with the code — they are checked by no one, so they drift and eventually lie (lesson D18).
  • Tests verify the contract only at the specific points you sampled; between those points they say nothing. They are existence proofs, not universal ones.
  • Names are advisory; a misleading name compiles fine (lesson D17's xTaskNumber wart proves it).
  • The type is re-verified on every compilation, over the whole input space it constrains, at zero marginal cost to you. It is the one part of the design the compiler has agreed to police forever.

So "machine-checked" is not a slogan; it's the specific property that the other three contract-carriers lack, and it's why a guarantee expressed as a type is categorically stronger than the same guarantee expressed as a comment, a test, or a name.

4. It's the most durable decision — a claim about cost asymmetry

Implementations are cheap to change because a body has one caller: the compiler. A published signature is expensive to change because its callers are everyone. That asymmetry means a type decision, once shipped, has the longest half-life of anything in the design — xTaskCreate's shape has held for ~20 years while its body was rewritten many times. The strategic consequence cuts both ways: get the type right and you've made a decision that keeps paying dividends across every future caller; get it wrong and every caller inherits the mistake, and you can't fix it without breaking all of them. High durability is high leverage and high stakes — which is exactly why it deserves the most review attention.

Deep dive — Hyrum's Law, the honest caveat on "durable"

Durability has a dark twin. Hyrum's Law: with enough users, every observable behavior of your interface — not just its typed contract — becomes something someone depends on. A signature that stays fixed can still have callers depending on undocumented timing, error ordering, or side effects the type never promised. So "the type is durable" guarantees the typed contract is stable, not that you're free to change everything the type doesn't mention. This is why C-module later pairs types with configASSERT contracts (C14) and can't-fail design (C15): the type pins down what it can, and the other tools pin down what the type can't express. Durable, but not total — state both halves.

The strongest case against the thesis (steelman)

You asked to know why the received wisdom is true, which means taking its opposition seriously. Here is the best case against "types are the review surface," made as strongly as its advocates would make it — followed by an honest synthesis, not a dismissal.

The case against
  1. Types don't catch the bugs that matter. The expensive defects are semantic — wrong logic, race conditions, off-by-one, a mis-modeled requirement. A function can be perfectly typed and completely wrong. Reviewing types can give a false sense of safety precisely because the signature looks clean.
  2. Dynamic languages ship fine. Python and JavaScript run much of the world with no static types; whole communities argue the productivity gain of skipping them exceeds the safety loss, and that tests cover the contract better anyway.
  3. Over-typing is its own complexity. A signature drowning in generics, wrapper types, and type gymnastics can be less obvious than a plain one — ceremony masquerading as rigor. A shallow module with an elaborate type is still shallow (lesson A2).

The synthesis. Every point above is true, and none of them contradicts the thesis as scoped. The thesis never claimed types catch most bugs — it claimed the highest marginal return on attention. Point (1) actually supports it: because a clean signature is quick to verify, it frees your scarce attention to spend on the semantic review where the expensive bugs live — the type is the surface you clear fastest so you can get to the hard part. Point (2) is a claim about writing code, not reviewing it under an LLM flood; and notice the industry's revealed preference — TypeScript, typed Python, Sorbet — is a decade-long migration toward types precisely as codebases scaled. Point (3) is real and is why blade-4 durability and A2 depth are constraints on good typing: the goal is types that carry contract, not types that perform rigor. So the honest position is not "types are all that matter" — it's "types are the highest-leverage surface to review first, and a necessary-not-sufficient foundation for the semantic review that follows." That scoped claim survives the steelman intact.

Red flag to name in reviews A function whose signature can't be understood without reading its body — a void* that means five different things, a bool whose meaning flips on a sibling argument, an int return that's sometimes a count and sometimes an error code. The signature is failing its one job: carrying the contract. Say it: "I can't call this safely from the signature — I have to read the implementation. Push the meaning into the types." Under-typed signatures are an LLM's default output (it optimizes for a body that works, not an interface that constrains); this is your standing objection.
