The struct you're not allowed to see

Lesson 2 asked whether a module is deep. This one asks how it got that way. The answer is almost always the same move: a design decision was sealed inside the implementation so it never reached the interface. In C, that move has a name and a mechanism — and the kernel runs it in two lines.

Why this lesson: "The model slopifies my abstractions" usually means it let an internal decision escape into the interface — a leaked field, a struct in the header, a getter that exposes the representation. To catch that in a PR you need to see hiding and its failure, leakage, as concrete, nameable things. Today you watch the kernel hide an entire data structure in plain sight.

The idea: depth comes from hiding

Ousterhout's mechanism for making modules deep is information hiding: bury each design decision inside one module's implementation so it never appears in the interface.1 The failure mode is its mirror image — information leakage: a decision that shows up in the interface, or in more than one module, so callers now depend on knowledge they should never have needed.2

hidden good

The decision lives in exactly one implementation. Callers can't see it, can't depend on it, aren't broken when it changes. The interface stays tiny — the module stays deep.

leaked costly

The decision is visible — a public field, a header struct, a shared format. Now N callers know it. Change it and you get change amplification across all N. The interface bloats — the module goes shallow.

The reviewer's test Point at any design decision (a data layout, an algorithm, a lock scheme, a wire format) and ask: how many modules know this? The strategic answer is one. If a caller can name it, depend on it, or break when it changes, it has leaked.

What this does not claim. "Hide information" is not "make every field private," not "wrap all data in getters," and not a security property (an opaque handle stops coupling, not an attacker). The precise claim is about design decisions that are likely to change: those belong in exactly one module. Plenty of things are legitimately public — a plain value type, a stable constant, a config struct the caller is meant to fill in (lesson B8's xTaskCreateStatic buffers). A public field is a leak only when it exposes a decision callers could then depend on. Hiding the wrong things — or hiding reflexively — is its own cost, which the steelman below makes concrete.

Specimen: the handle that hides a data structure

Open ./reference/FreeRTOS-Kernel/include/queue.h. This is the entire definition of a queue that a caller is ever given:

/* queue.h — everything the caller sees of a queue's shape */
struct QueueDefinition;   /* forward-declared: named, but no body */
typedef struct QueueDefinition * QueueHandle_t;

./reference/FreeRTOS-Kernel/include/queue.h — lines 50–51

That first line is an incomplete type: the struct is named but its members are not declared here. A caller can hold a QueueHandle_t (a pointer to it), pass it around, and store it — but the compiler will refuse to let them dereference it or touch a field, because from the header's point of view the struct has no fields. The wall isn't a convention or a comment. It's enforced by the type system.

Now open ./reference/FreeRTOS-Kernel/queue.c and look at what that handle actually points to — the body that only the implementation can see (abridged):

/* queue.c — the body, visible ONLY inside the implementation */
typedef struct QueueDefinition
{
    int8_t * pcHead;            /* storage area           */
    int8_t * pcWriteTo;         /* next free slot         */
    union {
        QueuePointers_t xQueue;      /* fields when it's a queue     */
        SemaphoreData_t xSemaphore;  /* fields when it's a semaphore */
    } u;
    List_t xTasksWaitingToSend;      /* blocked senders, priority-ordered */
    List_t xTasksWaitingToReceive;   /* blocked receivers                 */
    volatile UBaseType_t uxMessagesWaiting;
    UBaseType_t uxLength, uxItemSize;
    volatile int8_t cRxLock, cTxLock;   /* ISR-era lock counters */
    /* ... plus fields that appear ONLY under
       configSUPPORT_STATIC_ALLOCATION, configUSE_QUEUE_SETS,
       configUSE_TRACE_FACILITY ... */
} xQUEUE;

./reference/FreeRTOS-Kernel/queue.c — lines 103–136

Count what just got hidden behind those two header lines. Every one of these is a design decision the caller never learns, never depends on, and never breaks when it changes:

  • That a semaphore reuses this exact struct — via the union u. That's how Lesson 2's "a semaphore is a queue" is physically true. The reuse decision is sealed in here.
  • How blocked tasks are tracked — two priority-ordered lists. Callers just see "it blocks"; the bookkeeping is invisible.
  • The whole ISR concurrency scheme — cRxLock / cTxLock. A caller of xQueueSend never learns locks exist.
  • Which fields even exist — several members appear only under config macros. The struct's size and shape change with the build, and no caller can encode an assumption about it.
Verdict The opaque handle (a typedef'd pointer to an incomplete type) is information hiding rendered in C, and enforced by the compiler. One header line buys a wall that a dozen internal decisions hide behind — which is precisely why the queue module reads as deep. Depth isn't a vibe; it's the count of decisions you managed to keep on one side of that wall.

What leakage would have looked like

Picture the "helpful" version — the one an unsupervised LLM writes because it's convenient: put the full struct QueueDefinition body in queue.h. It compiles. It even feels friendlier: now a caller can write if( q->uxMessagesWaiting > 0 ) instead of calling an API. And that is the catastrophe:

  • Every file that includes queue.h now depends on the layout. Add a trace field, reorder the union, rename cRxLock — and you recompile and potentially rewrite the world (change amplification).
  • The union trick becomes load-bearing public knowledge; you can never quietly change how semaphores are stored again.
  • Callers poke uxMessagesWaiting directly, racing the very lock scheme that field exists to protect. The concurrency decision leaked, so it can now be violated.

Same behaviour on day one. On day one hundred, one is a kernel refined for twenty years and the other is unshippable. That contrast — one wall, decisions hidden vs no wall, decisions leaked — is the judgment you're training.

Deep dive — the exact price C charges for that wall, and why the kernel pays it

Opacity is not free, and naming its cost is what keeps this from being dogma. Because callers never see struct QueueDefinition's body, they also can't ask its size — sizeof(QueueDefinition) is a compile error outside queue.c. That single consequence forces the whole design: the queue must be constructed through the module, so its memory is either heap-allocated inside xQueueCreate or supplied blind as an opaque StaticQueue_t byte-blob the caller declares but cannot inspect. You lose stack allocation of a real queue, you lose field-level debugging without the internal header, and you pay one pointer indirection on every access. The kernel accepts all of it — because of the very thing the union in the struct revealed: the layout genuinely changes with build config (configUSE_QUEUE_SETS, trace, static-alloc). A caller who could see the struct would encode assumptions that a different build silently breaks. So opacity here isn't taste; it's the price of a struct whose shape is not stable, paid to buy a handle that is. (Lesson C12 studies this handle as a topic in its own right.)

The strongest case against reflexive hiding (steelman)

Encapsulation has a serious opposition, and a strategic reviewer can state it better than its critics. Then synthesise.

The case against
  1. Opacity costs real ergonomics. You can't sizeof it, can't stack-allocate it, can't inspect fields in a debugger without internal headers, and you eat indirection. For a small, stable struct that's pure friction — hiding buys nothing and taxes everyone.
  2. Getter/setter theatre. "Hide everything" degenerates into a wall of pass-through accessors that expose the same fields one call at a time — the representation leaks anyway, now with more boilerplate and a shallower interface.
  3. Premature encapsulation. Hiding a decision behind an interface before you know the right boundary can freeze the wrong abstraction — sometimes exposing the data and refactoring later is cheaper than guessing the wall's location now.

The synthesis. Each critique lands on bad hiding, and the scoped claim already excludes it. The test was never "hide everything" — it was "hide the decisions likely to change." A small, genuinely stable value type fails that test, so (1) is not a counter-example, it's the rule working: don't wall off what won't move. Point (2) is the deepest — a screen of getters that hand out every field is leakage wearing a trench coat (lesson A5's void * pvOwner shows the alternative: expose a capability, not the representation). Point (3) is real and is why hiding follows Parnas's rule — wall off the axis you can predict will change (lesson B9), not every axis speculatively. The queue passes all three tests at once: its layout demonstrably changes with build config, so hiding it is neither premature nor theatrical — it's the one decision most worth sealing.

Munger inversion — measure hiding by what breaks Don't ask "is this encapsulated?" — invert it: "if I changed this layout tonight, how many files would fail to compile tomorrow?" One (the implementation) means the decision is hidden. A dozen means it has leaked, and you've just measured the blast radius of a change you haven't even made yet. The kernel's answer is always one file — which is why twenty years of internal rewrites never broke a caller. Leakage is just a large blast radius you can't see until you light the fuse.
Red flag to name in reviews A struct definition in a public header when callers only need a handle; a "convenience" getter that returns an internal field by reference; a comment like "callers may read x directly." The words: "This leaks the representation — every caller now depends on a decision that should live in one place. Hand them an opaque handle and an accessor, and keep the layout private."
