Deep doors, small handles

The single most useful lens a reviewer owns: is this module deep or shallow? Learn to see it, and half of "this abstraction feels wrong" becomes something you can actually say out loud.

Why this lesson: "The models slopify my types and abstractions" is really a complaint about shallowness. To catch it in a PR you need a crisp, defensible test for module depth. Today we build that test on a genuinely beautiful piece of the FreeRTOS kernel.

The idea in one picture

Ousterhout: a module has an interface (what a caller must know) and an implementation (the code behind it). Depth is the ratio.1

deep good

Small interface, large functionality. A tiny door onto a big room. You learn a little, you get a lot. Cost < benefit.

shallow costly

Large interface, little functionality. You pay almost the full implementation cost just to use it. Often a thin wrapper. Cost > benefit — a net negative even when the code "works."

The reviewer's test For any module, ask two questions: (1) How much must a caller know to use it? (interface size — parameters, ordering rules, error modes, invariants they must maintain). (2) How much work does it do on their behalf? (hidden functionality). Deep = little knowledge buys much work. Shallow = much knowledge buys little.

What depth does not claim. Hold the scope precisely, because it's easy to over-read. Depth is a claim about the ratio of hidden functionality to interface size — not that big modules are good, that fewer methods are always better, or that a deep module is correct. A module can be beautifully deep and still compute the wrong thing; depth measures the quality of the abstraction boundary, not the logic behind it. Nor does "shallow" mean "delete it": some thin modules earn their place (a stable adapter over a volatile dependency — lesson B7). The test tells you the cost/benefit of an interface, which is one input to judgment, not the whole verdict.

Specimen: a semaphore is a queue

Open ./reference/FreeRTOS-Kernel/include/semphr.h. Near the top, the entire type definition of a semaphore is this:

/* semphr.h */
typedef QueueHandle_t SemaphoreHandle_t;

./reference/FreeRTOS-Kernel/include/semphr.h — line 38

That's not a typo or a shortcut. It's a design decision worth pausing on. A semaphore in FreeRTOS is a queue of length 1 that stores items of size 0 — you don't care about the data, only whether the queue is "full" or "empty."2 "Give" pushes; "take" pops. So the entire semaphore/mutex family is built by reusing the queue — one deep implementation, several interfaces on top:

/* semphr.h — a "create" is a thin, honest wrapper over the queue */
#define xSemaphoreCreateBinary()  \
    xQueueGenericCreate( ( UBaseType_t ) 1, semSEMAPHORE_QUEUE_ITEM_LENGTH, \
                         queueQUEUE_TYPE_BINARY_SEMAPHORE )

./reference/FreeRTOS-Kernel/include/semphr.h — line 167

Now weigh the queue module itself against the reviewer's test. The caller writes:

xQueueSend( q, &msg, xTicksToWait );

Three arguments. What the implementation does for them, hidden entirely behind the interface:

  • copies the item into the queue's storage,
  • if full, blocks the calling task for up to xTicksToWait and puts it on a waiting list,
  • when space appears, unblocks the highest-priority waiter,
  • and may trigger a context switch so that waiter runs immediately.
Verdict A handful of parameters buys you inter-task communication, blocking, timeouts, priority-ordered wakeups, and scheduling. That is a deep module — and it's so deep that semaphores and mutexes could be built on it for free. Depth compounds: deep modules make other modules simpler.

What shallow would have looked like

Imagine the tactical-tornado (or unsupervised-LLM) version: separate SemaphoreStruct, BinarySemaphore, CountingSemaphore, and Mutex types, each with its own create/give/take/delete, each re-implementing a waiting list and timeout logic. It would "work." It would also quadruple the interface, leak the same waiting-list decision into four modules (information leakage), and quadruple the bugs. Same behaviour, four times the complexity. That contrast — one deep module vs four shallow ones — is the strategic judgment you're training.

Deep dive — the second-order effect, and why "deep" is not "as much hidden as possible"

Two things the ratio alone hides. First, depth compounds: because the queue hid enough real machinery, semaphores and mutexes were built on it for free — a deep module makes the modules above it simpler, so the payoff is not linear in one interface but multiplied across every client that reuses it (lesson A5 is this effect at full scale). Second, depth has a failure twin: a "God object" that hides a hundred unrelated decisions behind one interface also scores well on "much work per token" — yet it is a design disaster, because the hidden things don't belong together (lesson B10). So the real test is not "maximise hidden functionality" but "hide the decisions that cohere behind the smallest honest interface." The queue passes because everything it hides serves one job: move items between tasks safely. Depth without cohesion is just a big bucket.

The strongest case against the depth lens (steelman)

Take the best case against using deep-vs-shallow as your primary tool, made as its advocates would — then an honest synthesis.

The case against
  1. It's unmeasurable. "Interface size" and "functionality" have no units. Two reviewers can look at the same module and disagree on whether it's deep — so it's just "elegant/inelegant" with a diagram, and it loses arguments to anyone who says "looks fine to me."
  2. Thin wrappers are often correct. Adapters, facades, ports-and-adapters seams, and stable public names over volatile internals are all deliberately shallow — and good. A rule that flags them all as "cost without benefit" cries wolf.
  3. Depth can hide too much. A very deep module can bury a decision you actually needed to see — a lock policy, a performance cliff, an allocation. Sometimes the shallower interface that surfaces the important knob is the better design.

The synthesis. All three are real and none breaks the lens as scoped. On (1): the test isn't a metric, it's a question — its value is that it turns "feels wrong" into a specific, answerable "how much must a caller know vs. how much do they get?", which is exactly the sentence that wins a review because the other person now has to answer it too. On (2): the lens agrees — that's why depth is a cost/benefit ratio, not a size rule, and why B7 studies precisely when a thin seam is worth it; "shallow" is a prompt to ask "what is this hiding?", not an automatic delete. On (3) it fully concedes and sharpens: the goal is to hide the decisions that should be hidden and surface the ones the caller must own (lesson B8 is that judgment). So the honest position is "deep-vs-shallow is the first and highest-yield question to ask, not the last word" — which survives the steelman intact.

Munger inversion — find the shallow module by trying to break it Don't ask "is this deep?" — invert it: "what would I have to know to use this safely, and how much of that is the module's job to have hidden?" If the honest list of things-you-must-know is nearly as long as the module's own code, you've found a shallow module without needing a metric. The tell is a wrapper you can't use without reading its body — the interface failed to buy you anything.
Red flag to name in reviews A "wrapper" whose interface is as large as the thing it wraps, and that adds no hidden work, is a shallow module — a classic LLM output. The right words: "This wrapper isn't deep — the interface is as big as what it delegates to, so it adds cost without hiding a decision. What is it hiding?"

Skill drill: judge the module

For each, apply the two-question test before answering. Deep or shallow?
