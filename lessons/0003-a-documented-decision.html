The comment that pays rent

Most comments restate the code. A rare few record a decision — the tradeoff, the evidence, the escape hatch. Learning to recognise (and demand) those is a strategic skill LLMs almost never volunteer.

Why this lesson: The scariest AI-era failure isn't wrong code — it's plausible code whose hidden assumptions no one wrote down. Your job is to surface why. This lesson shows you the gold standard, in the kernel, so you know what to ask the model to produce.

Obviousness, and its enemy

Ousterhout's rule: if code isn't obvious, that is a defect — the cost is paid by every future reader.1 But some decisions cannot be made obvious from the code alone, because the important information is the reasoning that was rejected. For those, the strategic move is to write the reasoning down where the reader will stand.

Specimen: the volatile that isn't there

Open ./reference/FreeRTOS-Kernel/include/list.h. The list structures are modified from inside interrupts. Any embedded developer's reflex is: those members must be volatile. They aren't. A tactical reader assumes a bug. Instead, they find this (abridged):

/*
 * The list structure members are modified from within interrupts, and
 * therefore by rights should be declared volatile. However, they are only
 * modified in a functionally atomic way (within critical sections or with
 * the scheduler suspended) ... Therefore, in all use cases tested so far,
 * the volatile qualifier can be omitted ... for a moderate performance
 * improvement without adversely affecting functional behaviour. The
 * assembly instructions generated by the IAR, ARM and GCC compilers ...
 * has been inspected and deemed to be as intended. That said, as compiler
 * technology advances ... it is feasible that the volatile qualifier will
 * be needed ... then the volatile qualifier can be inserted ... by simply
 * defining configLIST_VOLATILE to volatile in FreeRTOSConfig.h.
 */
#ifndef configLIST_VOLATILE
    #define configLIST_VOLATILE   /* expands to nothing */
#endif

./reference/FreeRTOS-Kernel/include/list.h — lines 65–95

Read what this comment is made of. It's not describing the code; it's defending a decision. Four moves, every one strategic:

  • Names the obvious objection first — "by rights should be volatile." It meets the reader's reflex head-on instead of hoping they don't notice.
  • States the reason it's safe — access is functionally atomic (critical sections / scheduler suspended), so the guarantee volatile gives isn't needed here.
  • Shows the evidence — they inspected the generated assembly on IAR, ARM, and GCC. Not "trust me" — "we checked."
  • Admits the risk and ships an escape hatch — future compilers might break this, so there's a one-line config (configLIST_VOLATILE) to reinstate volatile without editing the kernel.
The pattern to steal Objection → justification → evidence → escape hatch. That is what a load-bearing design decision looks like when it's written down well. When you review — human or LLM code — a non-obvious choice with none of these is not "clever," it's a liability. The strategic reviewer's question is simply: "Where's the comment that would let the next person change this safely?"

What this does not claim. This is not "comment more," and definitely not "comment everything." Ousterhout's first rule still stands: make the code obvious, and a comment that merely restates obvious code is noise that will rot into a lie. The scoped claim is narrow: for the rare decision whose rationale cannot be recovered from the code — because the important information is the reasoning that was rejected — write that reasoning down where the reader stands. Most lines need no such comment. The skill is spotting the few that carry a decision, not sprinkling prose everywhere.

Why this is your AI-era leverage

An LLM will happily generate the opposite of this: it'll silently add volatile "to be safe" (tactical, plausible, slower), or silently omit it, with no rationale either way. It optimises for code that looks right, not for decisions that are legible. You supply what it can't: the demand that a non-obvious choice carry its reasoning. Concretely, your review comment becomes "State the assumption that makes this safe, the evidence, and how someone reverses it" — and suddenly the model's output is auditable.

Deep dive — why this rationale can't live in a type, a test, or a name

It's fair to ask: if comments rot, why not encode the decision somewhere machine-checked? Try it, and you find the decision is irreducibly a comment. A type can say "this field is a TickType_t," but there is no type for "omitting volatile is safe because access is functionally atomic on the compilers we tested." A test can check behaviour on today's compiler, but the whole point of the comment is a claim about future compilers it cannot run. A name can't carry a paragraph of tradeoff. What the kernel does instead is the best available move: it makes the reversal itself machine-actionable via configLIST_VOLATILE, so the decision stays prose but its undo button is code. That split — rationale in a comment, reversal in a config knob — is the pattern to copy whenever a decision can't be typed. (Lesson C11 argues the converse: push into types everything you can, precisely so the residue left for comments is small and load-bearing like this one. Lesson D18 returns to comments as a design tool.)

The strongest case against comments (steelman)

There's a serious, popular position that says comments like this are a smell. Take it at its strongest, then synthesise honestly.

The case against
  1. Comments lie. Nothing forces a comment to track the code, so it drifts; a confident, out-of-date comment is worse than none because you trust it. The only honest documentation is the code itself.
  2. A comment is an apology for unclear code. If you needed a paragraph to explain the decision, the design failed — refactor until the code makes the decision obvious, and the comment becomes unnecessary.
  3. Nobody reads them. Under deadline, the comment is the first thing skipped and the last thing updated, so investing in prose is investing in something that decays untended.

The synthesis. Points (1) and (3) are true — and they are an argument for fewer, better comments, which is exactly the scoped claim, not against this one. This comment is not restating code that could be made clearer; it is recording information that is not in the code and cannot be: the rejected alternative, the compilers inspected, the reason the obvious choice was declined. No refactor makes "we omitted volatile and checked the assembly on IAR/ARM/GCC" fall out of clean code — which dismantles point (2): a comment is an apology only when it explains what the code does; it is load-bearing when it explains why the code is the way it is against a plausible alternative. The rot risk in (1) is real, so the kernel does two things to fight it: it keeps the rationale next to the exact #define it governs (so a change to one stares at the other), and it ships the escape hatch so the comment stays actionable, not decorative. Honest position: comment the why that can't be coded, delete every comment that merely echoes the what.

Munger inversion — write for the person who will undo you Invert the comment: don't write it for the reader who agrees, write it for the future maintainer who is about to "fix the bug" by adding volatile back in. What must they know to not make a mistake — and, if the decision really has expired, to reverse it safely? The kernel's block answers exactly that person: it names their objection, shows why it was declined, and hands them the one-line switch. A non-obvious decision with no such comment is a landmine you set for your own successor.
Red flag to name in reviews A non-obvious construct (a missing qualifier, a magic constant, an ordering requirement, a clever bit-trick) with no recorded rationale. Don't ask "is it correct?" — ask "how would the next person know it's correct, and how would they change it?" That question is the job.
