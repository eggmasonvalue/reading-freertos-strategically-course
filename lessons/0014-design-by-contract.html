The promises the type can't make

C13 ended on a wall C won't build. This is how the kernel builds it anyway — not in the type, but as an executable precondition. Design by Contract is where you recover the guarantees the type system is too weak to state — and it comes with a sharp, honest limit you must say out loud.

Why this lesson: C13 showed the type system has holes; the semaphore-as-queue misuse was one. Design by Contract (Bertrand Meyer)1 is the disciplined way to fill them: state each routine's preconditions, postconditions, invariants as checkable assertions. In the AI era this does double duty — a contract is both a spec the reviewer reads and a tripwire that fires at the exact line an LLM's plausible-but-wrong call violates it.

The idea — and the distinction the whole lesson turns on

A contract splits responsibility between caller and callee, explicitly:

  • Precondition — what the caller must guarantee before calling (the handle is non-NULL; the item size is zero for a semaphore).
  • Postcondition — what the callee guarantees on return.
  • Invariant — what stays true across the object's whole lifetime.
Precondition ≠ error handling (get this exactly right) A precondition is not error handling. Error handling copes with situations the API promises to handle — a full queue, a timeout — conditions that are expected and part of the contract. A precondition is a usage rule that must never be violated; breaking it is a bug in the caller, not a runtime condition to recover from. The consequence is a design fork: an expected failure gets a return value the caller must check (lesson C15); a should-never-happen violation gets an assertion that halts. Confusing the two produces both bugs — swallowing real usage errors, and "handling" things that can't legitimately occur.

Specimen: hundreds of contracts, verified

I counted, rather than trusting the roadmap. configASSERT appears 56 times in queue.c, 118 in tasks.c, and 264 across the kernel's .c files. Most kernel functions open by stating their contract:

/* queue.c — the precondition, executable, stated first */
BaseType_t xQueueGenericReset( QueueHandle_t xQueue, ... )
{
    configASSERT( pxQueue );                     /* line 311: handle MUST be non-NULL */
    ...
}
/* xQueueSemaphoreTake — encodes "this must be a semaphore, not a data queue" */
configASSERT( pxQueue->uxItemSize == 0 );         /* line 1355 */

./reference/FreeRTOS-Kernel/queue.c — lines 311, 1355

Read what each one is: a machine-checked sentence of the spec, placed exactly where it's owed. "You may not pass me NULL." "You may not use this semaphore handle as a data queue." These are precisely the promises C11's type couldn't encode and C13's alias couldn't enforce — now stated as code that fires the instant a caller lies. Line 1355 is the literal runtime backstop for the C13 hole: the compile-time wall was traded away, and this assert is where the guarantee was moved to.

The escape hatch — and the tradeoff it names configASSERT is defined by the port; if a project doesn't define it, it expands to nothing: 
/* FreeRTOS.h:97 (verified) */
#ifndef configASSERT
    #define configASSERT( x )        /* compiles away to zero cost */
#endif
So contracts cost nothing in production and catch bugs in development — the same documented-decision-with-a-knob shape you met in A3. But state the sharp edge plainly: a precondition only protects you on builds where it's enabled. It is a development-time tripwire, not a runtime guarantee shipped to the field.

Where DbC sits in the stack — defence in depth

Stack the module so far and the logic is clean: push each guarantee to the cheapest layer that can hold it. The type (C11) checks what it can, for free, at compile time, always. The opaque handle (C12) makes whole classes of misuse unexpressible. Where the type is too weak (C13's holes), the contract (C14) states the rule as a runtime check — and only there, for the promises the compiler genuinely can't make. A reviewer who sees a function with a non-obvious usage rule and no assertion asks: "where's the contract that would catch me getting this wrong?"

Deep dive — fail-fast, and why it matters more in embedded than anywhere

The deeper value of an assert isn't that it detects a bug — a test could do that — it's where and when it detects it: at the precise line the contract broke, before the corruption propagates. A NULL handle passed to a queue without the assert doesn't fail at the call; it fails later, somewhere in the body, after a wild write has scrambled memory — a bug whose symptom is arbitrarily far from its cause. On a desktop that's a painful debugging session; on a microcontroller with no MMU, no memory protection, and a watchdog reset as your only safety net, a propagated corruption can be unreproducible and safety-relevant. configASSERT converts "silent corruption discovered three seconds and one stack-smash later" into "halt, right here, at the guilty line." That fault-containment — fail fast, fail local — is why a safety-critical kernel spends 264 of them, and it's the same instinct as Ousterhout's "just crash" tactic in C15: for a truly impossible state, stopping is safer than limping on with corrupt invariants.

The strongest case against leaning on Design by Contract
  1. The check is gone exactly when you need it. Asserts are compiled out in release. So the contract protects the developer's bench but not the deployed product — the field failure, the one that matters, runs with the tripwire removed. That can breed false confidence: "it's asserted" feels safe while shipping unprotected.
  2. C only really does preconditions. Meyer's full DbC — postconditions, class invariants, and their inheritance semantics — needs language support C lacks. What you get in C is a pile of entry-point ifs, not the coherent contract system Meyer designed; calling it "Design by Contract" oversells it.
  3. Asserts can mask missing error handling. A lazy author asserts a condition that is actually an expected runtime failure, turning a recoverable case into a crash — the precondition/error-handling confusion, weaponized.

Synthesis. Points (1) and (3) are the real risks and they sharpen the discipline rather than defeating it. On (1): the mitigation is to keep asserts enabled through every layer where bugs are still economically catchable — unit tests, integration, HIL, and often early field/beta builds — so the tripwire is present across the entire span where caller-bugs are found, and only removed once the cost (timing, footprint) genuinely dominates. The point isn't "asserts protect production"; it's "asserts collapse the distance from bug to detection everywhere you can still afford to look." On (3): the fix is the precondition/error-handling distinction above — assert only should-never-happens; return-and-handle the expected. On (2): fair — in C this is really "precondition checking," the reachable slice of Meyer's idea, and honesty about that is better than grandiosity. So DbC in C is a complement to types and error design, not a substitute: types for what's checkable free and always; error returns for expected failures; assertions for the impossible-if-correct, live wherever you can still catch a bug cheaply.

Red flag to name in reviews A function with a genuine precondition (must be non-NULL; must hold the lock; index in range) that is neither encoded in a type nor asserted — it trusts the caller and corrupts silently when trusted wrongly. Say it: "This has an unstated precondition. Make it unrepresentable if you can, else assert it — don't leave it to hope." And its twin: "This configASSERT is guarding an expected failure — that should be a checked return, not a crash." LLMs both omit precondition checks (the happy path "works") and over-assert recoverable cases; you catch both.
