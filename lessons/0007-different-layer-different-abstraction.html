Strategic Programmer / Lesson 07 / ~13 min / Module B

Each layer should speak a different language

Module A trained your eye on single modules. Module B is about how they stack. The first test of a healthy stack is brutally simple: as you move from one layer to the next, does the vocabulary actually change? When it doesn't, you've found a layer that isn't earning its keep.

Why this lesson: "Clean architecture" is the LLM's favourite alibi for shipping four layers that all say the same thing — a controller calling a service calling a manager calling a repository, each method just relaying the last. Ch. 7 gives you the X-ray to see through it: a real layer boundary is where the abstraction changes. Learn to demand that change, and you can shrink a model's tower of relays to the one layer that was doing work.

The idea: adjacent layers, different abstractions

Ousterhout's Ch. 7 rule: in a well-designed system, each layer provides a different abstraction from the layers above and below it.1 When two adjacent layers have the same abstraction, that's a red flag — the clearest symptom being the pass-through method: a method that does little but call another method with roughly the same signature. It adds interface (cost) without adding functionality (benefit) — a shallow module wearing a layer's clothes.

What this does not claim. It is not "fewer layers are better," nor "indirection is waste," nor "every pass-through is a crime" (Specimen B below is a good one). The scoped claim is about abstraction change across a boundary: a layer earns its place by offering a different vocabulary than its neighbours. A layer that restates its neighbour's abstraction unchanged is the suspect — not because indirection is bad, but because that particular indirection translated nothing. Layers that introduce a real new abstraction (or a real variation seam) are exactly what you want, however many there are.

real boundary

Crossing it, the nouns change: "task" becomes "stack frame" becomes "CPU register." Each layer restates the problem in a lower vocabulary. The layer earns its existence.

fake boundary

Crossing it, the nouns are identical: service.save() calls manager.save() calls repo.save(). Nothing was translated. The middle layers are pass-through — pure cost.

Specimen A: a real boundary — "task" descends to "register"

Follow two related layer descents in the FreeRTOS stack and watch the language change under you. In the first, the public API layer speaks in terms of a task:

xTaskCreate( vMyTask, "blink", 128, NULL, 2, &handle );  /* "make me a task" */

Inside the kernel layer (tasks.c), "task" dissolves into TCBs, stacks, and ready lists — and at one point it must ask a lower layer to lay out a brand-new stack so the task looks like it was already running. It calls:

/* tasks.c — kernel asks the port to build a stack frame */
pxNewTCB->pxTopOfStack = pxPortInitialiseStack( pxTopOfStack, pxNewTCB->pxStack,
                                                pxTaskCode, pvParameters, ... );

./reference/FreeRTOS-Kernel/include/portable.h — lines 121–127

That is one descent: the kernel asks the port to construct a stack frame. A second descent starts at the stable kernel-facing taskYIELD name and crosses into the port layer. There the abstraction has completely changed — no tasks, only the register-level convention for requesting a context switch. Here's the Cortex-M3 portYIELD rendered in the machine's own words:

/* portable/GCC/ARM_CM3/portmacro.h — the SAME intent, in hardware vocabulary */
#define portYIELD()                                     \
    {                                                   \
        /* Set a PendSV to request a context switch. */ \
        portNVIC_INT_CTRL_REG = portNVIC_PENDSVSET_BIT; \
        __asm volatile ( "dsb" ::: "memory" );       \
        __asm volatile ( "isb" );                     \
    }
#define portNVIC_INT_CTRL_REG  ( *( ( volatile uint32_t * ) 0xe000ed04 ) )

./reference/FreeRTOS-Kernel/portable/GCC/ARM_CM3/portmacro.h — lines 85–96

Verdict Two descents, three vocabularies: task → TCB / stack for task creation, and taskYIELD → PendSV bit at address 0xe000ed04 for a context-switch request. Each boundary restates a stable kernel intent in the lower layer's language. That is what a load-bearing layer boundary looks like — and why FreeRTOS runs on dozens of chips: only the bottom layer speaks hardware, so only it changes per port. The boundary is a seam for variation.

Specimen B: the honest borderline (train your judgment, not a rule)

Now the uncomfortable one. In task.h:

/* task.h */
#define taskYIELD()            portYIELD()
#define taskENTER_CRITICAL()   portENTER_CRITICAL()

./reference/FreeRTOS-Kernel/include/task.h — lines 227, 241

By shape, these are textbook pass-throughs: taskYIELD() calls portYIELD() with the same (empty) signature and adds nothing. A dogmatic reviewer shouts "red flag!" — and a strategic one pauses, because the interesting question isn't "is it a pass-through?" but "what is this thin line buying?" Here it buys a stable, kernel-facing name at a variation seam: application and kernel code say taskYIELD, while the thing it forwards to (portYIELD) is swapped out wholesale for every architecture. The relay isn't inventing a fake middle layer; it's a one-line adapter that decouples the stable name from the volatile implementation.

That's the judgment to internalise: a pass-through shape is acceptable only when it sits on a real boundary and pins a name that must stay stable while the other side varies. Absent that — a service.save() that only ever calls one repo.save(), no variation, no rename worth having — the same shape is pure waste. Same code shape; opposite verdicts, decided entirely by whether an abstraction (or a variation axis) actually changes across the line.

Deep dive — pass-through variables, and why the macro relay is nearly free while the OO one isn't

Ch. 7 names a second, sneakier symptom: the pass-through variable — a parameter threaded down through layers that don't use it, just to reach a layer that does. It couples every layer it passes through to a decision none of them care about, and it's worse than a pass-through method because it's invisible in any single function (you only see it by tracing the whole call chain). The cure is the same as the method's: either give an intermediate layer a way to supply the value (so it stops travelling), or share it through a context object rather than the signature. — Second point worth seeing: why the kernel tolerates #define taskYIELD() portYIELD() so cheaply. It's a macro: at compile time the relay vanishes, so the only cost is one name to learn, and that name buys a portability seam. Contrast a Service→Manager→Repo tower in an OO codebase: each relay is a real method, a real stack frame, a real class to open while debugging, and a real thing the reader must hold in working memory. Same "pass-through" shape, wildly different cost — which is why the reviewer's question is never "is there indirection?" but "what does this indirection translate, and what does it cost to keep?"

The strongest case for more layers (steelman)

Architecture culture is full of reasons to add the layers Ch. 7 would delete. State the best of them, then synthesise.

The case against collapsing
  1. Layers are test seams. A service-over-repository split, even with matching signatures, lets you mock the repository and unit-test the service in isolation. The "pass-through" is what makes the code testable.
  2. Dependency inversion. Hexagonal / ports-and-adapters deliberately introduces interfaces whose methods mirror the domain's — so the domain depends on an abstraction, not a concrete DB. That mirroring looks like a pass-through but is the whole point.
  3. Today's relay is tomorrow's extension point. The moment you need caching, retries, or a second implementation, the layer that was "just forwarding" becomes the place it all hangs. Delete it and you'll rebuild it under pressure.

The synthesis. Notice what every point smuggles in: a reason the layer is not actually a pass-through. A seam you can mock (1), a dependency-inverting port (2), a place caching will live (3) — each is a real abstraction or variation axis the layer introduces, which is precisely what Ch. 7 asks for. So they don't refute the rule; they name the test that passes it. The rule bites only on the layer that offers none of these — no seam anyone mocks, no second implementation, no cross-cutting concern, just get calling get. Point (3) deserves the sharpest answer, because it's the usual alibi: "might need it later" is B9's speculative-generality trap — add the layer when the second implementation or the caching arrives (it's a cheap refactor then, with a real abstraction to hang on it), not now on spec. Honest position: keep every layer that translates a vocabulary or isolates a variation; collapse the ones whose only defence is a future that hasn't shown up.

Munger inversion — make each layer prove it exists Don't ask "are these layers clean?" — invert it: walk the stack and demand of each layer, "what noun do you introduce that your caller didn't already have?" A real layer answers instantly: task → stack frame → PendSV bit. A fake layer stammers — it says "save," and so did the layer above it. The one that can't name its new abstraction (or the variation it hides) is not a layer, it's a toll booth on every call that crosses it. Find the fake layers by trying, and failing, to name what they translate.
Red flag to name in reviews A layer whose methods mostly forward to the layer below with unchanged names and signatures, on a boundary where nothing varies. The words: "These layers share one abstraction — the middle one is pass-through. Either it should translate to a genuinely lower-level vocabulary, or it should be deleted and the caller should talk to the layer below directly." Make the model justify each layer by naming the abstraction it introduces; if it can't, collapse it.
