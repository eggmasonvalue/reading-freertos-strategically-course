Names are a tax you pay once and collect forever

A precise name is documentation that can't go stale — it's read at every use. Module D turns to readability, and it opens where reading begins: the name. The FreeRTOS prefix convention is a superb case study — but only if you split it into the half that's brilliant and the half that's a known anti-pattern.

Why this lesson: Naming is the readability lever with the highest duty cycle — every reader, every use, forever. LLMs generate names that are locally plausible but globally inconsistent; a strategic reviewer enforces the codebase's convention and demands names that carry precise meaning. But "carry the type in the name" is exactly the kind of received wisdom you should not swallow whole — half of it is genius and half of it is the thing every naming guide warns against. This lesson separates them.

The principle (APoSD ch14)

Ousterhout: a good name is an image in the mind of what the thing is — precise, consistent, non-misleading.1 The diagnostic he draws from it: if a name is hard to choose, or keeps wanting to be vague, that's usually a symptom that the underlying design is muddled — the thing doesn't have one clear responsibility. So naming isn't just labeling; it's a probe into whether the abstraction is clean.

Specimen: the Hungarian prefix scheme, decoded

FreeRTOS encodes a variable's type in its name. With the key, dense declarations become legible at a glance:

UBaseType_t  uxPriority;      // ux = UBaseType_t (unsigned)
void *       pvParameters;    // pv = pointer to void
const char * pcName;          // pc = pointer to char
BaseType_t   xOverflowCount;  // x  = BaseType_t / struct / "other"
void         vTaskDelay(...);  // v  = returns void  (you met this in C15)
                              // pd = a #define constant (pdTRUE, pdPASS)

./reference/FreeRTOS-Kernel/include/task.h — declarations throughout (e.g. lines 143, 156–157)

The distinction that unlocks the whole debate: Apps vs Systems Hungarian

This convention is one of the most-argued topics in programming, and most of the heat comes from people not making a distinction that Joel Spolsky drew sharply2. There are two Hungarian notations, and they are almost opposites:

Systems encode the compiler's type

Prefix says what the machine type is: ux=unsigned, pc=char*. This is what FreeRTOS uses. Critics' objection: it's redundant with the declaration the compiler already knows, adds noise, and rots when a type changes but the name doesn't.

Apps encode the kind/meaning

Prefix says what the value means in the domain: us=unsafe string, row/col, dx=a delta. The compiler can't check this, so the name is the only signal — and mixing unsafeString into a safeString slot now "looks wrong."

The insight that connects it to Module C Apps Hungarian is C13's "make illegal states unrepresentable," done in names instead of types. When your language can't give a "sanitized string" its own type, encoding kind in the name makes the illegal mix look wrong to a human reviewer — a poor-man's newtype wall. That kind of Hungarian is genuinely valuable and survives every critique. Systems Hungarian — which is what the kernel actually uses — is the kind naming guides rightly attack: it duplicates information the type already carries. So the honest verdict on FreeRTOS is split: it uses the weaker of the two Hungarians, and it does so for reasons that were defensible in its context, not because Systems Hungarian is good in general.

So why did a great codebase pick the weaker kind? The tradeoff, priced

bought what it gains here

Type/signedness/return travels with every use, even far from the declaration — valuable in 2004-era embedded C with no IDE hover, reviewed on paper or in diff. And because widths are portable typedefs (BaseType_t varies by target), the prefix flags signedness bugs the raw type name alone would obscure across ports.

paid what it costs

Newcomers must learn the cipher first (obscurity for the uninitiated). Names are noisier. And the prefix can lie when maintainers slip — which is worse than no prefix, because readers trust it.

The wart — proof that Systems Hungarian rots In task.h, in the task-status struct: 
UBaseType_t xTaskNumber;   /* line 171 (verified) */
By the scheme an unsigned UBaseType_t should be ux-prefixed — this one is x. The name now claims "other/signed-ish" while the type is unsigned: a small lie, harmless here, but it's the exact failure mode critics predict for Systems Hungarian — the prefix and the type drift apart because nothing enforces their agreement (unlike an actual type, which the compiler checks — C11 blade 3). A naming convention is only as obvious as the discipline maintaining it.
The strongest case against this convention
  1. It's redundant and rots. The compiler already knows the type; encoding it in the name duplicates a fact that can — and did (xTaskNumber) — fall out of sync. Redundant, unchecked information is a liability.
  2. Modern tooling makes it pure noise. With a language server that shows the type on hover, the prefix adds visual clutter for zero information. In 2024 TypeScript it would be indefensible.
  3. It couples names to types. Change a variable's type and you must rename it everywhere or the name lies — friction that discourages exactly the refactors you'd want.

Synthesis. The critique is correct about Systems Hungarian in a modern context — and that's the lesson, not a defense. The strategic reading has three moves. Decode: read the convention fluently so the code is legible (done). Judge in context: Systems Hungarian earned its cost in a portable, safety-critical C kernel with primitive-era tooling and cross-target typedefs; the same scheme in a modern typed language with a language server is pure noise — the tool already tells you the type, so the prefix is clutter that can only rot. Context, not fashion, decides. Enforce or migrate, but don't mix: whatever a codebase chose, hold every new name (yours or the model's) to it, because an inconsistent convention is worse than either pure choice — it trains readers to trust a signal that sometimes lies. And separately: wherever your language can't type a distinction that matters (sanitized vs raw, safe vs unsafe), reach for Apps Hungarian deliberately — that half is timeless, and it's C13 wearing a different hat.

Red flag to name in reviews A diff that introduces names in a different style from the surrounding file — the classic LLM tell, because the model averages over many codebases instead of matching this one. Say it: "This name is fine in the abstract but breaks the convention this file uses — match the local style, or we've made the codebase less obvious, not more." And the higher-order one: "This prefix encodes the type the compiler already checks; if we want a name to carry a distinction, make it carry the kind, not the machine type."
