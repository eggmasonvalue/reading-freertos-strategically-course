The error that isn't

The best way to handle an error is to design so it cannot occur. Every error a caller must check is a branch to write, test, and get wrong. Ousterhout's move is to reduce not the handling but the number of errors that exist — and the honest catch is that "eliminated" often means "absorbed somewhere you should be able to point to."

Why this lesson: LLMs generate error-handling by the yard — if (err) {…} after every call, much of it for failures that can't happen. That noise is complexity, and complexity is where slop hides. The strategic counter is to recognize (and design) APIs whose signature says "this cannot fail," so the branch doesn't exist to get wrong. But you must also see where the difficulty went when an error "disappears," or you'll mistake masking for magic.

The principle (APoSD ch10), ranked by power

Errors are a leading source of complexity because each one multiplies the paths a reader must hold in mind. Ousterhout's four tactics1:

  1. Define the error out of existence — redefine the semantics so the "error" becomes a normal case (deleting something absent is a no-op success, not a failure).
  2. Mask it — handle it at a low level so higher levels never see it.
  3. Aggregate — handle many errors in one place instead of at every call.
  4. Just crash — for truly unrecoverable violations (this is what C14's configASSERT does).

Keep tactic 1 and tactic 2 distinct in your mind — the steelman below turns on the fact that they're easy to confuse, and that what looks like "defined out of existence" is frequently "masked, well."

Specimen: read the return types as promises

The kernel's signatures tell you, before you read a line of body, which operations can fail and which can't — and many were deliberately designed into the second group:

/* CAN fail — and the type forces you to notice (this is C11 again) */
BaseType_t xQueueReceive( QueueHandle_t xQueue, void * pvBuffer,
                          TickType_t xTicksToWait );   /* pdTRUE / pdFALSE: may time out */

/* CANNOT fail — the void return IS the promise */
void vTaskDelay( const TickType_t xTicksToDelay );   /* delaying always "succeeds" */
void vTaskDelete( TaskHandle_t xTaskToDelete );      /* deleting is defined to just work */

./reference/FreeRTOS-Kernel/include/queue.h — lines 913–915

./reference/FreeRTOS-Kernel/include/task.h — lines 840, 894

Read the leverage xQueueReceive returns BaseType_t because a timeout is a real, expected outcome the caller must branch on — that error genuinely exists, so the type surfaces it. But vTaskDelay returns void: the designers arranged the semantics so there is nothing to fail. The absence of a return value is not laziness — it's a promise, and it deletes a branch from every one of the thousands of call sites. Multiply that: the API's error surface shrank by design, and with it the state space every caller (and every test, and every LLM) must cover.
Deep dive — where the difficulty actually went in vTaskDelete

"Deleting always succeeds" sounds too clean, so follow the hard case: a task deleting itself. It cannot free its own stack — it is currently running on that stack; free it and the next instruction executes on reclaimed memory. A naive API would have to fail or forbid this. FreeRTOS instead absorbs the difficulty: vTaskDelete puts the doomed task on a xTasksWaitingTermination list and returns; the Idle task later runs prvCheckTasksWaitingTermination → prvDeleteTCB and frees the memory from a safe context (tasks.c lines 2269, 2330–2335, verified). So the error wasn't conjured out of reality — it was masked (tactic 2): relocated to a place that can handle it cleanly, so the caller's interface can honestly promise void. That is the real craft, and the honest reading: "defined out of existence" at the interface is very often "masked, well" underneath — and a strategic reviewer can point to where. If you can't point to where the difficulty went, it wasn't handled; it was ignored.

The naming convention encodes the promise

You've been decoding the Hungarian prefixes (lesson D17). Here they pay off as a contract readable at a glance: a v... function returns void — it tells you in its name "no result to check"; an x... function returns a BaseType_t you're expected to inspect. The kernel's own convention sorts its API into can-fail / can't-fail before you even reach the return type. Error design, made visible in the name — exactly the obviousness a reviewer should demand, and a small proof that D17's "convention as information" is real value, not just ceremony.

The strongest case against "define errors out of existence"
  1. It can hide bugs, not just errors. Redefining "delete an absent thing = success" also silences the case where its absence was itself a bug you'd have wanted to know about. A no-op success can convert a loud failure into a quiet wrong-behavior — strictly worse.
  2. "Just crash" is a luxury many domains don't have. Ousterhout's tactic 4 assumes crashing is acceptable. You cannot crash a brake controller or a pacemaker; "halt on the impossible" must become "enter a defined safe state," which is more error machinery, not less.
  3. Masking destroys observability. Push errors down and handle them silently, and the higher layers lose the signal — you can't diagnose, meter, or alert on a failure the API swallowed. Fewer branches can mean less insight into a misbehaving system.

Synthesis. Each objection is a boundary condition on the tactic, not a refutation — and together they define which tactic to reach for. Point (1) says: define out of existence only when the "error" is genuinely a normal case in your domain's semantics; if absence is sometimes a bug, keep it observable (assert it, per C14, or return it). Point (2) says: in hard-real-time/safety, replace "crash" with "transition to safe state" — the principle (don't limp on with broken invariants) survives; only the mechanism changes. Point (3) is the sharpest: masking is powerful but must not be silent — mask the caller's obligation to handle the error while preserving the system's ability to observe it (a counter, a trace hook — note FreeRTOS keeps traceQUEUE_* hooks exactly here). So the mature rule isn't "delete all errors"; it's: an error should exist at exactly one layer — the one that can actually resolve it — and be observable from above even when it's handled below. The goal is fewer obligations on the caller, not less truth in the system.

Red flag to name in reviews An API that returns an error code no caller can do anything useful with — the only honest response is to assert or ignore it. Say it: "What can a caller actually do with this failure? If nothing meaningful, design it out — make it a no-op success, mask it at the layer that can resolve it, or crash/safe-state on the truly impossible — but keep it observable. Don't hand back a status nobody can act on." And its inverse: "This no-op-success is swallowing a case that's sometimes a real bug — keep it observable."
