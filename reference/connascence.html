Connascence — coupling you can name

A precise vocabulary for coupling, so a review comment can say which coupling and how to weaken it instead of "this feels coupled." Two components are connascent if changing one forces a change in the other to keep the system correct.1 Ranked below by strength (how hard to refactor). The strategic move is almost always: convert a stronger form into a weaker one.

Static connascence — visible in the source (weakest → strongest)

FormTwo parties must agree on…Weaken it by…FreeRTOS specimen
Namethe name of a thing. Rename the entity, update every reference. Unavoidable; the weakest.— (this is the floor; aim to land here)every call to xQueueSend

Dynamic connascence — only visible at run time (stronger; hunt these first)

FormTwo parties must agree on…
Execution (order)the order in which things run — call init() before use().
Timingthe timing of execution — a race, a required delay, a deadline.
Valueseveral values must change together to stay consistent (an invariant across variables).
Identitymultiple entities must refer to the same instance (same object, not just equal).

Dynamic forms are generally stronger than static ones: the compiler can't see them, so they fail at run time and resist refactoring tools. When you spot one, that's your first refactor target.

The three properties (how you reason about any instance)

StrengthHow hard is it to refactor away? Weaker (Name) is easier to change than stronger (Algorithm, or any dynamic form). Prefer weaker.
LocalityHow close are the two parties? Strong connascence inside one small module is fine; the same strength across a module boundary is a problem. Distance raises the cost of strength.
DegreeHow many entities are entangled? A protocol shared by 2 sites is cheaper to change than one shared by 40. Prefer lower degree.
Weirich's rules of thumb (how to use all of the above):1
  1. Minimise overall connascence by splitting the system into well-encapsulated elements.
  2. Minimise connascence that crosses boundaries (long distance × any strength = pain).
  3. Maximise connascence within a boundary — it's cheap when local, so keep entangled things together.
  4. When stuck with coupling, convert a stronger form into a weaker one (Position/Meaning → Name is the everyday win).
The review one-liner this buys you Instead of "this is coupled," say: "That's connascence of position across a module boundary — pass a named struct to make it connascence of name." Naming the coupling and prescribing the downgrade is the whole skill.
