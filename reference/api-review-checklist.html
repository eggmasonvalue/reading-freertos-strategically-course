API Review Checklist

The compressed output of Module C. Run this top-to-bottom on any interface — a teammate's PR, your own draft, or an LLM diff. Each item is a question to ask and a sentence to say when the answer is wrong. The goal is one interface the compiler, the caller, and the model all fall into using correctly.

First pass — the type carries the contract (C11–C13)

1. Does the signature carry its own contract? C11 · review density

Can I call this correctly from the signature alone, without reading the body?

Say: "This signature isn't carrying its contract — I have to read the implementation to call it safely. Push the meaning into the types."

2. Are internals hidden behind an opaque handle? C12 · info hiding

Is a struct body sitting in a public header where callers can touch fields they shouldn't?

Say: "This type is transparent — its layout is now everyone's dependency. Forward-declare it, move the body to the .c, expose only the accessors we need." (Cost: caller can't size it → provide a constructor / static-buffer variant.)

3. Are illegal states unrepresentable? C13 · type-driven

Do two things that must not be swapped share one typedef alias (both just uint32_t / char* / same handle)?

Say: "These are the same type to the compiler, so it'll let us swap them — an illegal state left representable. If the mix is a real bug, wrap each in its own struct." (Remember: typedef aliases; a struct makes a distinct type.)

Second pass — guarantees the type can't make (C14–C15)

4. Are preconditions stated and checked? C14 · design by contract

Is there an unstated usage rule (non-NULL, lock held, index in range) that's neither typed nor asserted?

Say: "This has an unstated precondition. Either make it unrepresentable, or assert it — don't leave it to hope." (A precondition is a caller bug, not a handled case.)

5. Do the errors that exist need to exist? C15 · define errors out

For each error return: can a caller do anything meaningful with it? Could the semantics be redefined so it can't occur?

Say: "What can a caller actually do with this failure? If nothing meaningful, design it out — no-op success, mask it lower, or crash on the impossible. Don't return a status nobody can act on." (A void return can be a promise.)

Third pass — craft (C16 · Bloch)

6. Easy to use right, hard to use wrong?

Is the correct call the obvious one? Can a plausible misuse even be written?

Say: "Make the wrong call hard to write — bake the constraint into the name or signature, like ...FromISR does with calling context."

7. Any boolean traps?

A bare bool/magic flag that's opaque at the call site (foo(x, true, false))?

Say: "These booleans are unreadable at the call site and swap-prone. Make them a named enum, or split into two well-named functions."

8. Consistent argument order & names?

Does the same concept sit in the same slot across the whole API? (Kernel: handle first, data next, control/timeout last.)

Say: "This argument order breaks the convention the rest of the API follows — least astonishment; line it up."

9. Small surface — when in doubt, leave it out?

Is anything in the public interface that callers don't need? (You can add later; you can't remove.)

Say: "Drop this from the public surface until a caller truly needs it — a smaller interface is a deeper module."
The one-line spine Types are the review surface (C11) → hide behind opaque handles (C12) → make illegal states unrepresentable (C13) → assert the contracts types can't hold (C14) → design errors away (C15) → finish with craft (C16). Read and shape an interface so the compiler, the caller, and the LLM all fall into the pit of success.
