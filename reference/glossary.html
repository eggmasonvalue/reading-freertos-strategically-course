Glossary

The shared vocabulary of the course. Every lesson uses these words precisely — that precision is itself the skill. Terms tagged Ousterhout come from A Philosophy of Software Design; FreeRTOS terms are specimen vocabulary you need only as far as a lesson requires.

Strategic-design vocabulary

Strategic programming Ousterhout
A mindset where working code is necessary but not sufficient; you invest ongoing effort in the design so complexity stays low over the codebase's life. Contrast with tactical. The AI-era edge: LLMs supply working code cheaply; your value is keeping the design coherent.
Tactical programming Ousterhout
A short-term mindset optimised for getting the next feature/fix working now, accreting complexity. The "tactical tornado" ships fast and leaves a mess others clean up.
Complexity Ousterhout
Anything about a system's structure that makes it hard to understand or modify. It has two root causes: dependencies and obscurity. It is felt, not counted — measured by the effort to make a change.
Dependency Ousterhout
When code cannot be understood or changed in isolation — a change here forces a change there. Not inherently bad; the goal is to reduce their number and make the remaining ones obvious.
Obscurity Ousterhout
When important information is not obvious — a name that misleads, a convention you must know but can't see, a dependency with no signal. The other root of complexity.
Symptoms of complexity Ousterhout
Three tells: change amplification (a simple change touches many places), cognitive load (how much you must know to make a change), and unknown unknowns (it isn't obvious what you must change — the worst).
Module / interface / implementation Ousterhout
A module is any unit with an interface and an implementation (a class, a file, a service). The interface is what a caller must know to use it; the implementation is the code that fulfils it.
Deep module Ousterhout
A module whose interface is small relative to the functionality it provides. A powerful capability behind a tiny door. The single most important idea in the course. Specimen: xQueueSend / xQueueReceive — a few args hide blocking, timeouts, task lists, and context switches.
Shallow module Ousterhout
A module whose interface is large relative to what it does — you pay nearly the full cost of the implementation just to use it. Often a thin pass-through wrapper. A net negative: its cost exceeds its benefit.
Information hiding Ousterhout
Embedding design decisions inside a module's implementation so they don't appear in its interface. The primary technique for making modules deep.
Information leakage Ousterhout
When a design decision shows up in more than one module — e.g. two modules that both must know a file format. Callers become coupled to knowledge they shouldn't need. The opposite of information hiding.
Connascence Page-Jones / Weirich
A ruler for coupling: two components are connascent if changing one forces a change in the other. Ranked by strength (name → type → meaning → position → algorithm → the dynamic forms) and judged by locality (strong coupling is fine locally, costly across a boundary) and degree. The strategic move: convert a stronger form into a weaker one. Full ranking in the cheat-sheet. Specimen: positional args of xQueueGenericSend (position); queueSEND_TO_BACK naming a magic 0 (meaning→name).
Obviousness Ousterhout
The property that a reader can understand code and interfaces quickly and correctly. If something is not obvious, that is a red flag — the cost is paid by every future reader (now including LLMs).
General-purpose vs special-purpose Ousterhout
"Somewhat general-purpose" interfaces tend to be simpler and deeper than interfaces specialised to today's single caller. Over-specialisation is a common source of shallowness.
Opaque handle Pattern
A caller-held token (typically a typedef'd pointer to an incomplete type) that represents an object whose fields are hidden. Information hiding for C. Specimen: TaskHandle_t, QueueHandle_t — you hold it, you can't see inside it.
Incomplete type C / Pattern
A type that is named but whose size and members are not (yet) declared — e.g. a forward-declared struct QueueDefinition; with no body in the header. You may form and pass a pointer to it, but the compiler forbids dereferencing it or touching a field. This is the compiler-enforced wall that makes an opaque handle real. Specimen: queue.h declares struct QueueDefinition;; the body lives only in queue.c.
Transparent type Pattern (anti-pattern)
The opposite of opaque: a struct whose full definition sits in a public header, so every caller can touch every field and the memory layout becomes de-facto public API. A prime source of information leakage — and the default an LLM reaches for so a caller can "just access X directly." Turning a transparent type opaque is a high-value review edit.

Specimen vocabulary (FreeRTOS — as needed only)

Kernel FreeRTOS
The core that decides which task runs and provides tasks, queues, semaphores, and timers. Our specimen lives in ./reference/FreeRTOS-Kernel/.
Task FreeRTOS
An independent thread of execution with its own stack, managed by the scheduler. Represented to callers by an opaque TaskHandle_t.
Queue FreeRTOS
The kernel's central data structure for passing data between tasks (and ISRs), with optional blocking. Notably, semaphores and mutexes are built on queues.
Semaphore / mutex FreeRTOS
Synchronisation primitives. In FreeRTOS a SemaphoreHandle_t is literally a QueueHandle_t — a deep-module reuse we study directly.
Hungarian prefix convention FreeRTOS
The kernel's naming scheme where a prefix encodes type/return (x=BaseType/struct, ul=unsigned long, pv=void*, pd=macro constant, v=void return). A convention that must be known — an obviousness tradeoff we critique, not worship.
configLIST_VOLATILE FreeRTOS
A config knob in list.h that lets a port re-add the volatile qualifier the kernel deliberately omits. Our exhibit A of a documented design decision with an escape hatch.
